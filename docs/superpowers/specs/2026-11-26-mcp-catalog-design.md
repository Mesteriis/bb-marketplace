# MCP Каталог — дизайн

Дата: 2026-11-26. Статус: черновик на одобрение владельца.

## Зачем

Владелец работает только в BB и хочет одно место в его интерфейсе, где можно:

- увидеть все MCP-серверы и управлять ими;
- найти новый сервер и поставить его в несколько кликов;
- не держать серверы в памяти без дела и не раздувать контекст агентов.

Сегодня управление стоящими серверами, остановка по простою и поиск инструментов по запросу уже есть в мосту
Agent Plugins (форк в `bb-marketplace`, `plugins/agent-plugins`). Не хватает коллекции серверов и установки из
интерфейса: новый сервер сейчас означает ручную правку пакета MCP в репозитории инфраструктуры владельца
(`mcp.json`, скрипт запуска в `bin/`, файл ключей в `~/.config/bb-mcp/*.env`).

## Цели

1. Новый плагин BB «MCP Каталог» с одним экраном в боковой панели.
2. **Поиск** серверов в официальном MCP Registry (`registry.modelcontextprotocol.io`, API `v0/servers`).
3. **Проверка** найденного сервера агентом до установки, с отчётом и решением владельца.
4. **Коллекция**: проверенные серверы хранятся в git (`bb-marketplace`), ставить можно только из неё.
5. **Установка** из коллекции: форма просит только нужные переменные; секреты не показываются повторно.
6. **Управление стоящими**: список всех серверов моста (и поставленных каталогом, и пакетов из infra) со
   статусом, включением и выключением, одобрением, входом OAuth и удалением поставленных каталогом.
7. Эффективность сохраняется: каталог ничего не держит запущенным; серверы живут на мосту с его остановкой по
   простою и поиском инструментов по запросу.

## Не цели

- Свой MCP-шлюз, прокси или запуск серверов: всё это остаётся у моста.
- Изменение поведения или устройства моста. Каталог работает поверх него через команду `bb agent-plugins`;
  единственная правка форка — команда включения и выключения сервера (см. «Решения владельца»).
- Перенос существующих пакетов infra в каталог. Они остаются как есть и только показываются в списке.
- Запись в настройки провайдеров (`~/.claude.json`, `~/.codex/config.toml` и т. п.).
- Поддержка нескольких машин в первой версии: только машина, где стоит BB.

## Анти-цели (провал, даже если работает)

- Можно поставить сервер, минуя проверку и коллекцию.
- Секрет попал в git, в лог, в ответ агента или в повторный показ формы.
- Каталог тянет инструменты серверов в контекст агентов или держит процессы запущенными.
- Плагин требует правок в мосту, из-за которых обновления от автора форка становятся ручным слиянием.

## Ограничения

- Правила `bb-marketplace`: плагин — самостоятельный пакет в `plugins/<name>/`; `src/core` и `src/ui` без хост-кода,
  хост — через адаптеры `src/adapters/bb`; `npm run check` и `npm run build`; манифесты меняются вместе.
- Сторонний код ставится только через маркетплейс владельца. Коллекция — тот же принцип для MCP-серверов.
- Коммит и push в `bb-marketplace` — только по явному действию владельца.
- Все тексты интерфейса и отчётов — по-русски.

## Подходы (рассмотрены, выбран первый)

| Подход | Плюсы | Минусы |
|---|---|---|
| **Свой плагин «MCP Каталог» поверх моста** (выбран) | Один экран для всего; мост не трогаем, обновления форка идут как раньше | Ещё один плагин на поддержке; экран Agent Plugins остаётся как технический |
| Вкладка «Каталог» в форке моста | Всё в существующем экране | Форк расходится с автором, каждое обновление — ручное слияние |
| Навык «поставь MCP X» без экрана | Дёшево | Не «выбрать в интерфейсе», а просить агента |

Владелец выбрал первый вариант и источник «реестр для поиска, ставить только проверенное».

## Как устроено

### Экран

Одна страница в боковой панели, три вкладки:

- **Стоящие** — все серверы моста из `bb agent-plugins list --json` и `show <id> --json`: пакет, сервер, статус
  (`running`, `idle`, `needs approval`, `needs auth`, `error`), число инструментов. Действия: включить или выключить
  (`setMcpEnabled`), одобрить и запустить (`approve`), войти (`auth`), для поставленных каталогом — изменить
  переменные и удалить. Пакеты из infra помечены «из infra» и не удаляются отсюда.
- **Коллекция** — проверенные серверы с короткой выжимкой отчёта проверки; кнопка «Поставить».
- **Поиск** — запрос в реестр, результаты с источником (npm, PyPI, Docker, удалённый адрес), версией и датой.
  Кнопка «Проверить» для каждого; уже стоящие и уже проверенные помечены.

### Коллекция (в git)

Папка `mcp-collection/` в `bb-marketplace`, по одной папке на сервер:

- `server.json` — запись из реестра, закреплённая на версии (без «latest»);
- `review.md` — отчёт проверки по-русски: источник и лицензия, что запускается, сетевые адреса, файловая система,
  требуемые переменные, риски, вердикт;
- `entry.json` — решение владельца (`approved`, дата, проверенная версия, разрешённые транспорты) и, при
  необходимости, ограничения (например, только чтение).

Индекс коллекции — `mcp-collection/index.json`, проверяется скриптом манифестов при коммите.

### Проверка

«Проверить» создаёт тред BB (провайдер и модель — по умолчанию владельца для обычной работы, Sonnet) с заданием:
скачать указанную версию в отдельную пустую папку, прочитать код и манифест, оценить по чек-листу навыка
`external-agent-pack-audit`, написать `review.md` и черновик `entry.json` в рабочую копию `bb-marketplace` на
отдельной ветке. Владелец читает отчёт в треде и нажимает в каталоге «Принять в коллекцию» или «Отклонить».
Принятие — коммит на ветке проверки, слияние в `main` и push (см. «Решения владельца»). Без принятия запись в
коллекцию не появляется.

При принятии каталог заново берёт из реестра запись проверенной версии и требует, чтобы `server.json` в коммите
совпадал с ней (JSON с отсортированными ключами), а `entry.json` называл то же имя и ту же версию. Индекс
проверяется против `main`, от которого начиналась проверка, а перед коммитом пересобирается из текущего `main`
со строкой этого сервера: запись, принятая за время проверки, не мешает. В индексе одна строка на сервер.

### Установка

Для принятой записи каталог генерирует локальный пакет Agent Plugins в данных плагина
(`<plugin data>/packages/<server-name>/`): `plugin.json`, `mcp.json`, скрипт запуска `bin/run.sh`. Скрипт:

- npm — `npx -y <пакет>@<закреплённая версия>`; PyPI — `uvx <пакет>==<версия>`; Docker — `docker run --rm -i
  <образ>@<digest>`; удалённый адрес — запись `streamable-http` без скрипта;
- читает переменные из файла `<plugin data>/env/<server-name>.env` (права 0600), который пишет форма установки;
- для серверов, которые не отвечают на пробный запрос моста, оборачивается шимом, как `markitdown` сейчас.

Затем каталог вызывает `bb agent-plugins install <путь>`, и сервер появляется на мосту. Первый запуск требует
одобрения в мосту (`approve`) — каталог показывает эту кнопку сам.

Ставить и обновлять можно только запись, принятую в этом каталоге: у каталога должна быть своя запись проверки в
состоянии «принято» для этого имени и этой версии, а её коммит принятия должен входить в `origin/main`
(`git merge-base --is-ancestor`). Иначе — ошибка «запись не принята в этом каталоге». Запись, принятая в коллекцию
другим экземпляром каталога, здесь не ставится.

Аргументы пакета (`packageArguments`, `runtimeArguments`): передаются только готовые значения — `value` или,
для обязательного аргумента, `default`; необязательный аргумент без значения не передаётся. Пакет с обязательным
аргументом без готового значения (или собранным из переменных-шаблонов) не ставится: «аргументы пакета пока не
поддерживаются». Аргументы времени выполнения идут до пакета (`npx`, `uvx`) или до образа (`docker run`),
аргументы пакета — после.

Обновление: новая версия из реестра снова проходит проверку. Агент проверки заменяет в индексе строку этого
сервера новой версией; каталог принимает только более новую версию (semver). После принятия каталог
перегенерирует пакет и вызывает `bb agent-plugins update`.

### Секреты

Форма установки берёт список переменных из `server.json` (`isSecret`, `isRequired`, `default`, описание).
Обязательная переменная без значения (ни введённого, ни сохранённого) останавливает установку на сервере:
«не задана обязательная переменная <NAME>». Несекретная переменная, оставленная пустой, получает `default`
сервера, если он есть; у секретных `default` не используется. Значения пишутся
только в файл 0600 в данных плагина, никогда не в git, не в базу снапшотов и не во фронтенд. Повторно форма
показывает «задано» без значения; можно заменить или очистить. Это тот же принцип, что у текущих файлов
`~/.config/bb-mcp/*.env`, только управляемый из интерфейса.

### Эффективность

Каталог сам ничего не держит запущенным и не даёт агентам инструментов. Его страница читает состояние моста по
запросу и по кнопке «Обновить». Остановка по простою (10 минут), сохранённый каталог инструментов и поиск
инструментов по запросу остаются у моста и работают для серверов каталога так же, как для остальных.

## Решения владельца

- Свой плагин поверх моста.
- Коллекция: поиск в официальном реестре, ставить только проверенное и принятое в свою коллекцию.
- Ключи — в интерфейсе, не правкой файлов вручную.
- **Включение и выключение стоящих серверов** — маленькой правкой форка моста: команда
  `bb agent-plugins enable|disable <id> <serverId> [--json]` поверх существующей функции `setMcpEnabled`.
  Правка отправляется автору моста как предложение. Это единственное изменение моста; цель «мост не трогаем»
  читается как «не меняем его поведение и устройство».
- **Нажатие «Принять в коллекцию» — согласие владельца** на коммит, слияние в `main` и push в `bb-marketplace`.
  Каталог коммитит запись в отдельную ветку, сливает её в `main` и делает push. Источник истины для установки —
  `origin/main` на GitHub: каталог читает коллекцию через `git fetch` и `git show origin/main:mcp-collection/…`,
  а не из рабочей копии. Запись на ветке, но не в `main`, не считается принятой.

## Интеграция с мостом (уточнено)

Команда `bb agent-plugins` уже умеет `list`, `show`, `install`, `update`, `remove`, `approve`, `auth` и
`tools` (проверено на установленной версии). Внутренние функции моста другим плагинам не открыты, поэтому
адаптер каталога вызывает CLI `bb` из серверной части плагина (`src/adapters/bb`) и разбирает вывод `--json`.
Мост копирует ставящийся пакет в свою папку (`~/.bb/plugins/agent-plugins/plugins/<id>/vN`), поэтому
расположение исходного пакета в данных каталога ограничений не создаёт. Свои пакеты каталог узнаёт по
`sourceIntent` вида `path:<данные каталога>/packages/…`.

## Проверка: как плагин ведёт тред

Тред проверки создаётся командой `bb thread spawn` в проекте `bb-marketplace` (провайдер Claude Code, модель
Sonnet, новое рабочее дерево на ветке `mcp-collection/<server>-<version>`). Агент проверки скачивает
закреплённую версию в пустую папку вне рабочего дерева, код сервера не запускает и пишет только
`mcp-collection/<server>/review.md` и черновик `entry.json` в своё рабочее дерево. Тред запускается с режимом
разрешений `auto` (`--permission-mode auto`): шаги агента в оболочке не ждут человека, но это не полный доступ.
Каталог хранит у себя `threadId` и ветку записи и опрашивает состояние треда (`bb thread … --json`):
«проверяется», «отчёт готов» (тред завершён и файлы на ветке есть), «ошибка» (тред упал или файлов нет).
«Принять» коммитит на этой ветке, сливает в `main` и делает push. «Отклонить» только записывает отказ; тред и
его рабочее дерево владелец архивирует сам.

Путь к рабочей копии `bb-marketplace` (`marketplaceRepoPath`) и проект маркетплейса для тредов проверки
(`marketplaceProjectId`) — настройки каталога, по умолчанию пустые. Пока настройка пуста, страница показывает,
что задать (и команду `bb plugin config <id> set <ключ> <значение>`), а действия, которым она нужна, выключены и
на сервере отказывают. Перед слиянием каталог проверяет, что основная копия на `main` и чистая; иначе
показывает причину и ничего не делает.

## Остаточный риск

- Вызовы RPC плагина внутри хоста BB не проверяются по вызывающему: любой код с доступом к RPC каталога в этом
  BB может вызвать «Принять» или «Поставить». Защита держится на том, что установка требует собственной записи
  принятия каталога и коммита в `origin/main`, а принятие — готовой проверки.
- Тред проверки работает с разрешениями `auto`: агент сам выполняет команды оболочки, в том числе скачивание
  недоверенного пакета. Правило «код не запускать» — указание агенту, а не техническая граница.

## Решения разработчика (можно оспорить)

- Коллекция живёт в `bb-marketplace` (`mcp-collection/`), рядом с плагинами: одна точка доверия.
- Пакеты, поставленные каталогом, — в данных плагина, а не в infra: это машинное состояние, а не код инфраструктуры.
- Секреты — файл 0600 в данных плагина, по образцу существующих пакетов.
- Проверку делает отдельный тред BB, а не сам плагин: так видно рассуждение и его можно продолжить.
- Версии закреплены; «latest» не ставится.
- Существующие пакеты infra не переносятся.
- Перед установкой каталог проверяет наличие нужного запускателя (`npx`, `uvx`, `docker`) по абсолютным путям
  и показывает ошибку; сам ничего не доустанавливает. Образ Docker закрепляется по digest, который агент
  проверки вписывает в `entry.json`; без digest установка невозможна.
- Все stdio-серверы запускаются через обёртку-шим, который отвечает на пробный запрос моста и дальше прозрачен
  (как у `markitdown`). Тестовый запуск недоверенного кода для этого не нужен.
- Агент проверки выбирает в `entry.json` один пакет или один удалённый адрес из `server.json`. Поддерживаются
  `environmentVariables` (значения из формы, `default` для несекретных) и готовые значения аргументов пакета;
  аргументы, которые надо вводить, пока не поддерживаются. Удалённые адреса в первой версии — только без
  секретных заголовков (OAuth делает мост); адреса с секретными заголовками отложены.
- «Ограничения» в `entry.json` — только отметки в отчёте, не защита: каталог их не принуждает.
- Удаление сервера каталогом удаляет его пакет из моста, сгенерированный пакет и файл с ключами.
- Имя плагина `mcp-catalog`.

## Оставлено разработчику

- Раскладка модулей по правилам `bb-marketplace` (`core`, `ui`, `adapters/bb`) и тесты.
- Точный формат `entry.json` и `index.json` и их проверка в `scripts/check-manifests.mjs`.
- Как каталог отличает свои пакеты в общем списке моста (по пути источника `path:<plugin data>/packages/…`).
- Кеширование результатов поиска в реестре и обработка постраничной выдачи (`nextCursor`).
