# Проверка SDK для Makosh Navigation

Дата: 2026-11-15. Проверены локальные декларации BB Plugin SDK 0.6.132,
используемого существующим mail-плагином. Проверка статическая, не live acceptance.

## Подтверждённые контракты

- `experimental_sidebarNavigation` позволяет зарегистрировать собственный rail.
- `experimental_useSidebarNavigation` предоставляет стабильные IDs, иконки,
  badge, активный пункт, видимость и host actions. За пределами sidebar hook
  возвращает пустой список: settings section не может использовать его напрямую.
- `settingsSection` размещает собственный React-редактор в настройках плагина.
- `PluginStorage.database()` предоставляет plugin-scoped better-sqlite3 database;
  транзакция и conditional update позволяют реализовать CAS по revision.
- `PluginRealtime.publish` рассылает ephemeral сообщения всем подключённым клиентам;
  канал не предоставляет изоляцию по аккаунту.

## Пробелы относительно согласованной спецификации

### Изоляция аккаунтов: блокирует production storage

`ExperimentalPluginRpcHandlerContext` содержит только `experimental_caller` и
`experimental_signal`. `BbContext` содержит `projectId` и `threadId`.
В проверенных контрактах нет доверенного account/user ID или lifecycle смены
аккаунта. SQLite расположен в области плагина установки; account-scoped storage
не заявлен. Caller `client` не является идентификатором пользователя.

Передача accountId от клиента не решает авторизацию. Общая realtime-рассылка
также не доказывает изоляцию. Поэтому нельзя честно реализовать и проверить
раздельные раскладки аккаунтов по имеющимся контрактам.

Варианты: одна раскладка на установку BB либо поддерживаемый account-scoped API
в хосте. Оба меняют согласованную техническую границу и требуют выбора владельца.

### Защита черновика при уходе из settings: блокирует этот путь UI

В проверенных frontend declarations и relevant authoring references не найден
публичный navigation blocker/guard для страницы настроек. `BbNavigate` позволяет
инициировать переход, но не перехватить произвольный переход хоста. Локальные
обработчики кнопок редактора и beforeunload не покрывают SPA navigation.

Варианты: расширить SDK либо сохранять валидные изменения автоматически,
показывая pending/error; невалидный/неподтверждённый draft можно удерживать в
plugin-local session state и восстанавливать при возврате. Последний вариант
отменяет согласованную семантику явного Save/Discard и требует согласования.

### Каталог неактивного провайдера

Bridge от активного rail к settings возможен в пределах экземпляра frontend,
но ещё не проверен harness-тестом. Для неактивного провайдера допустим последний
известный каталог с явным stale status и запретом полного reset, как предусмотрено
спецификацией. Публичный независимый API полного живого каталога пока не подтверждён.

## Статус и границы выполненного

Task 1: статическая часть выполнена; feasibility gate не пройден.
Scaffold/production code не создавались: план прямо требует подтвердить account
boundary до product implementation. Tests/build/live UI не запускались и не
считаются пройденными. Никакой плагин в работающем BB не установлен/не включён.
Изолированное дерево и согласованные документы сохранены. `zed-init --update`
создал конфигурацию для фактически существующего mail-компонента; navigation
должен добавляться только после появления пакета.

Следующий шаг: согласовать одну раскладку на установку + автосохранение либо
сохранить полную спецификацию и отдельно определить работу над SDK хоста.
