# S14. Архивы как источник и создание — спецификация helper-протокола

Статус: **ревизия 11 после повторного ревью astra+opus (repair)**, кода нет; ждёт повторного ревью.
Решения координатора A–H и правки ревью 1–7 внесены ниже (§3, §4, §5, §6, §7, §10, §11).
Основание: ADR 0002 (accepted), [план 2a, задача 7](../plans/stage-2a.md),
[приёмка S14](../../research/stage-2-libs.md#приёмка-s14), `docs/security.md`.
Исполнитель: тред `thr_c6npqvkrkw`.

## 1. Границы среза

Входит: чтение ZIP/ZIP64/TAR как панель-источник (`archive:<uuid>`), распаковка
(= план `copy`), создание ZIP/TAR (= план `pack`), пароль владельца, helper.
Не входит (явно отклоняется кодом `unsupported`, не молчаливо): изменение
существующего архива; `.tar.gz/.tgz/.tar.xz` и другие сжатия TAR (в ADR только
USTAR/PAX, `flate2` не в зависимостях); 7z/RAR; многотомные ZIP; sparse TAR;
шифрованный TAR; запись ZipCrypto; не-arm64/не-macOS.
Распаковка symlink/hardlink **не поддерживается**: `FileProvider` не умеет их
создавать. Такие записи показываются в списке и дают элементы плана `refused`
(§5).

## 3. Процесс helper

- Бинарник `bin/commander-archive-helper`, `cargo build --release --locked
  --target aarch64-apple-darwin`, `--remap-path-prefix` как у Remote Hub (без
  домашнего каталога в бинарнике). Крейты зафиксированы `=`:
  `zip =8.6.0` (`default-features=false`, `deflate`, `aes-crypto`),
  `tar =0.4.46` (`default-features=false`), `libc`, `serde`/`serde_json`,
  `base64`, `zeroize`. Новые зависимости — только с записью в notices.
- Платформа: `process.platform === "darwin" && process.arch === "arm64"`;
  иначе `ArchiveProvider` не создаётся, UI/агент получают ошибку
  `archives_unavailable` с текстом «Архивы недоступны: нет helper для
  платформы». Никакого JS-fallback.
- Запуск: `experimental_spawnHostProcess` (как Remote Hub), абсолютный путь,
  `env` очищен (без `HOME` с паролями и т. п.; только `PATH=/usr/bin:/bin`),
  `argv = []`, **единственный** допустимый аргумент `--version` (печатает
  `commander-archive-helper <версия>` и выходит). Пароль/пути в argv/env не
  передаются.
- До spawn: `checkHelperIntegrity(path)` — файл есть, регулярный, не symlink,
  `SHA256SUMS` рядом: ровно одна строка, `<64 hex>  commander-archive-helper`,
  сумма совпала, иначе `helper_checksum_failed` (`no_sums`, `malformed_sums`,
  `not_listed`, `duplicate`, `symlink`, `mismatch`). Режима «без проверки» нет.
  Тесты — те же литералы, что в `helper-integrity.test.ts` Remote Hub.
- Один процесс на открытый архив (изоляция памяти и сбоев; пароль не живёт в
  общем процессе). Срок жизни: закрытие stdin = выход; простой без запросов
  10 мин = выход (`idle_exit`); отмена задания, `close`, выгрузка плагина —
  `SIGTERM`, через 2 с `SIGKILL`, потоки закрываются. Не больше 4 одновременных
  helper-процессов (`too_many_open_archives`).
- Ресурсы (решение D). Ядро macOS может не применять `RLIMIT_AS`: первым
  шагом среза — тест на macOS arm64 (процесс выделяет сверх лимита; результат
  записывается в спецификацию и в `hello.rlimit_as: "enforced"|"not_enforced"|
  "failed"`). **На rlimit не опираемся.** Защита: ограниченные буферы (§4–§5),
  лимит CPU **на запрос**: перед каждым запросом helper читает `getrusage` и ставит один soft-предел `RLIMIT_CPU` = использованное + 120 с на запрос (hard **не трогает**, внутри запроса предел не обновляется, в том числе на data-кадрах); `SIGXCPU` → выход, адаптер видит `helper_crashed` и перезапускает по правилам §11; долгий `read` укладывается в бюджет запроса, дальше адаптер шлёт новые запросы, `RLIMIT_CORE=0`
  (пароль не попадает в core), тайм-аут на запрос **30 с без единого кадра**
  (длинный `read` шлёт data-кадры и не упирается; по истечении — `helper_crashed`
  с причиной `timeout`, SIGKILL), и **сторож RSS в адаптере**: опрос
  `proc_pidinfo(PROC_PIDTASKINFO)` (при недоступности — `ps -o rss= -p`) раз в
  1 с, порог 512 МиБ → SIGTERM, через 2 с SIGKILL, ожидание выхода процесса
  (`exit`-событие) до освобождения слота. Если `hello` сообщает, что rlimit не
  установился, адаптер продолжает работу только со сторожем (вывод в журнал
  кодов, не в UI). Тесты: helper, раздувающий память (тестовая feature
  `test-hooks`, не в релизном бинарнике), убит сторожем ≤ 3 с; зависший без
  кадров запрос — через 30 с (в тесте таймаут настраивается).
- Helper читает архив **только по файловому дескриптору, который сам открыл**,
  и открывает его обходом от корня endpoint (решение A): `open` получает
  `root` (корень `host:<id>` или каталог приватной копии, байты) и `segments`
  (сегменты пути, байты); helper делает `openat` по сегментам с
  `O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC` для каталогов и
  `O_RDONLY|O_NOFOLLOW|O_CLOEXEC` для последнего, затем `fstat` — регулярный
  файл. Абсолютный путь одной строкой helper не принимает.
  **Жёсткие правила обхода:** helper отклоняет `rootB64`, не являющийся
  абсолютным путём, и сегменты `""`, `"."`, `".."`, содержащие `/` или NUL
  (`invalid_path`); корень открывается `open(root,
  O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC)`; на macOS дополнительно `O_NOFOLLOW_ANY`
  (отказ при symlink в **любом** компоненте) как вторая линия. `rootB64`
  адаптер берёт **только из доверенного реестра endpoint** (корень
  `host:<id>` или серверный каталог копий, §7), не из RPC-запроса, не из
  агентского ввода. **Остаточный доверенный префикс (записан):** сам корень
  endpoint / серверный каталог копий — ссылки внутри корня helper не разрешает, но ссылки
  *в* пути до корня считаются доверенной конфигурацией.
  **Сверка:** `expect` для локального архива **обязателен**; первая сверка —
  `dev`, `ino`, `size`, `mtime` из `open.expect` (исходный `stat` адаптера) против `fstat` уже **открытого** fd **до** разбора (расхождение →
  `changed_since_open`, разбор не начинается); все последующие сверки
  сравнивают с **исходным отпечатком** (`dev, ino, size, mtime`), а не с
  предыдущим ответом. `verify` не принимает строку пути: helper заново обходит
  от корня по тем же сегментам через `openat`/`fstatat(AT_SYMLINK_NOFOLLOW)` и
  сравнивает `dev, ino, size, mtime` с `fstat(fd)`; symlink на месте файла или
  пропажа → `changed_since_open`.
  **Какой это endpoint — «машина сервера».** **В SDK 0.6.132 у `hosts.list()` такого флага нет.** Кандидат —
  `primaryHostId` из `bb.sdk.system.config()`, но равенство «основной хост =
  машина процесса сервера плагина» не доказано; **до доказательства на стенде
  всегда приватная копия (§7), без «пути без копии»** (записано как
  ограничение). Тест: файл подменён между предварительным
  `stat` и `open` (rename нового файла на место) → `changed_since_plan`. Предпроверка и разбор
  идут по одному дескриптору (Node не имеет `openat`, поэтому обход делает
  helper). Адаптер до `open` сверяет fingerprint архива с `expect` от
  `FileProvider` (`stat`), после `open` и после каждого запроса — снова; при
  расхождении — `changed_since_plan`, helper закрывается.
- Helper не пишет ничего, кроме: своего stdout (кадры) и каталога staging
  для `pack` (§6). Целевой FS задания helper не видит.

## 4. Кадры

```
[ u32 LE длина тела ][ тело ]
тело[0] = вид:  0x01 control (UTF-8 JSON)
                0x02 data    (тело[1..5] u32 LE reqId, тело[5..] байты)
                0x03 secret  (тело[1..5] u32 LE reqId, тело[5..] UTF-8 пароль)
```

- Потолок и минимум кадра. Длина тела читается до выделения буфера.
  control: `2 ≤ длина ≤ 1 МиБ` (`kind` + минимум `{}`); data: `5 ≤ длина ≤ 4 МиБ
  + 5` (kind + reqId; пустая полезная нагрузка допустима как «конец»); secret:
  `6 ≤ длина ≤ 1 КиБ + 5` (хотя бы один байт пароля). Длина 0 запрещена.
- **Направления.** `0x01` — в обе стороны; `0x02` — в обе стороны (helper →
  адаптер: ответ `read`; адаптер → helper: только `pack_data`); `0x03` — **только
  адаптер → helper**. Кадр не того направления — `protocol_error`.
- **Симметричная фатальная `protocol_error`** (на **обеих** сторонах:
  helper — выход с кодом 2; адаптер — SIGKILL helper, ожидание выхода,
  закрытие ресурса, `helper_crashed`): неизвестный вид; длина вне диапазона;
  невалидный JSON; невалидный UTF-8 (control и secret); чужой/неактивный
  `reqId`; `secret` без активного `need_password`; повторный `hello`;
  data-кадр без запроса, ожидающего data; обрыв на середине кадра; EOF между
  data-кадром и `ok`; второй запрос при занятом (один в полёте); ответ с
  `req`, которого нет. Тесты на каждый пункт — в Rust (helper как приёмник) и в
  TS (адаптер как приёмник, поддельный helper).
- Версия протокола `PROTOCOL_VERSION = 1`; первый кадр helper → адаптеру:
  `{"t":"hello","protocol":1,"helper":"0.1.0","zip":"8.6.0","tar":"0.4.46"}`.
  Адаптер сверяет `protocol` и `helper` с ожидаемыми константами; несовпадение —
  `helper_version_mismatch`, процесс завершается. Таймаут hello 5 с.
- Запросы идут с `reqId` (u32, выдаёт адаптер, не 0). Ответ — control
  `{"t":"ok"|"err","req":N,…}`; ответ `read` — data-кадр с тем же `reqId` +
  control `ok` после него. Запросы обрабатываются **последовательно** (один
  в полёте), кроме `cancel`. Параллелизм — несколькими процессами.
- Пароль: отдельный кадр `0x03`, **только** в ответ на `{"t":"need_password",
  "req":N}`; никогда в control JSON. **Честная модель (решение F):**
  пароль **хранит только helper** (`Zeroizing<Vec<u8>>`, стирается при
  `close`/выходе/неверном пароле сверх 3 попыток; не логируется, не попадает в
  сообщения об ошибках). Адаптер держит пароль `Uint8Array` **только до
  подтверждения helper-ом** (`ok` на `need_password`) и сразу `fill(0)`; после
  этого пароля в процессе плагина нет — при рестарте helper (решение E, G)
  владелец вводит его заново. Кадр `0x03`: только адаптер → helper, только в
  ответ на `need_password` **активного запроса владельца**; payload `0x03`
  исключён из любой трассировки, дампов, `stderr`-зеркал, тестовых записей
  трафика (кодек не отдаёт payload `0x03` в `toString`/`inspect`/журнал;
  тест проверяет, что запись трафика содержит для `0x03` только длину, а
  пароль-литерал не встречается ни в записи, ни в argv/env, ни в stderr).
  В БД, настройки, логи, ответы RPC и агенту пароль не попадает; агентское
  чтение пароль владельца не использует — шифрованный архив для агента →
  `auth_failed`/`password_required`; tool, принимающего пароль, нет.
  **Остаточный риск (записан):** пароль приходит из диалога UI через RPC как
  JS-строка (не стирается GC), ключевой материал внутри крейта `zip` не
  обёрнут в `Zeroizing`; процесс helper живёт до `close`.
- Логи helper — stderr, строго без путей содержимого и без имён записей
  (только коды и счётчики); адаптер читает не больше 64 КиБ stderr.

### Запросы

Все пути в сообщениях — `pathB64` (base64 сырых байт), имена записей — тоже
base64 сырых байт: форматы допускают не-UTF-8 имена.

| `t` | Поля | Ответ `ok` |
|---|---|---|
| `open` | `rootB64`, `segmentsB64[]`, `format: "auto"\|"zip"\|"tar"`, `limits: {maxTotalBytes, maxEntries, maxRatio}`, `expect: {size, mtimeNs, dev, ino}` (обязателен) | `{handle:1, format, fingerprint:{size, mtimeNs, dev, ino}, entries, totalSize, totalCompressed, encrypted:boolean, metaBytes}` или `need_password` сначала, если шифрованы имена/каталог (WinZip AES шифрует тела; имена в ZIP открыты — пароль нужен только на `read_open`) |
| `list` | `prefix` (байты, `""` = корень), `cursor: string\|null`, `limit ≤ 1000`; страница также ограничена **сериализованным размером control-кадра < 1 МиБ** (helper заканчивает страницу раньше и возвращает `cursor`; одна запись ≤ 16 КиБ в JSON гарантируется лимитом имени 4096 байт) | `{entries: ArchiveEntry[], cursor}` — прямые потомки `prefix`, в порядке индекса; промежуточные каталоги, которых нет в архиве, синтезируются (`synthetic:true`) |
| `stat` | `nameB64` | `{entry: ArchiveEntry\|null}` |
| `read_open` | `id` (индекс записи) | `{stream, size}`; шифрованная запись — `need_password` |
| `read` | `stream`, `length ≤ 4 МиБ` | data-кадр с байтами (0 байт = конец) и `ok{pos}` |
| `read_close` | `stream` | `ok` |
| `verify` | — | `{changed:boolean}`: обход от корня по сегментам `open` (§3, `fstatat(AT_SYMLINK_NOFOLLOW)`) и сравнение `dev, ino, size, mtime` с исходным отпечатком |
| `cancel` | `req` | `ok` (прерывает текущий запрос с `err cancelled`) |
| `pack_open` | см. §6 | |
| `close` | — | `ok`, затем выход 0 |

`ArchiveEntry`:
`{id:number, nameB64, name:string, nameLossy:boolean, kind:"file"|"dir"|"symlink"|"hardlink"|"special", size:string(bigint), csize:string, mtime:number|null, mode:number|null, encrypted:boolean, linkB64?:string, refused?:RefusedReason, synthetic?:boolean}`.
`name` — декодирование для показа: UTF-8; для ZIP без флага UTF-8 — CP437
(как делает `zip`), сырые байты остаются в `nameB64`; `nameLossy` — декодирование
потеряло данные. Идентификатор записи для чтения — `id`, а не имя.

Каждый `read_open`/`read` и каждый `list`/`stat` перед работой делает
`verify` внутри helper; расхождение — `err changed_since_open`
(адаптер превращает в `changed_since_plan`). Чтение записи — только
последовательное по `stream`; для произвольного `offset` адаптер закрывает
поток и открывает заново (повторное чтение тоже считается в лимитах).

**Барьер целостности (правка 1).** Данные записи нельзя отдавать в
`WriteSession.commit` до подтверждения целостности. Запрос
`{"t":"read_finish","stream":N}` → `ok{size, crc32:number|null, aes_auth:
boolean|null}` отдельным запросом: helper дочитывает поток до EOF записи,
сверяет фактический размер с заявленным (`size_mismatch`), CRC32 (`crc_mismatch`;
для TAR CRC нет — подтверждается только размер) или AES-аутентификацию
(`aes_auth_failed`). `readChunks` адаптера: не читает после заявленного размера
(`read` с `length` > остатка укорачивается; при `pos == size` не шлёт `read`),
для **пустой записи** `read` пропускается, а барьер `read_finish`
выполняется всё равно. Порядок раннера для записи: `read…` → `read_finish` →
`commit`. Ошибка `read_finish` → элемент `failed`, `abort()`, commit не
вызывается. Тесты: пустая запись → `read_finish` ok, файл создан пустым;
запись ровно в один чанк (4 МиБ); CRC неверен → отказ без commit; данные
усечены → отказ без commit.

## 5. Защиты (все до буферизации и до публикации)

Единая точка: helper отказывает **при `open`**, адаптер (`archive-guard.ts`)
повторяет проверки по именам и лимитам при построении плана — вторая линия.

### 5.1 TAR (свой сканер до `tar::Archive`)

1. Один проход по 512-байтовым заголовкам (`pread` по `offset`, тела
   пропускаются `seek`, буфер фиксированный 512 Б). Проверяются: checksum
   (знаковый и беззнаковый вариант), `magic` (`ustar\0`/`ustar `), тип.
   Допустимые типы: `0`/`\0` файл, `5` каталог, `2` symlink, `1` hardlink,
   `3`,`4`,`6` special (`special`, не распаковываются), `L`,`K`,`x`,`g`
   служебные. Любой другой, `S` (sparse), `D`/`M`/`V` — `unsupported_format`.
2. Размер: octal (с проверкой цифр) или base-256 (бит 7 первого байта) —
   `checked_*` арифметика; отрицательное base-256, переполнение `u64`, а также
   `offset + 512 + round_up(size, 512) > file_len` → `truncated` или
   `size_overflow`. **Конец архива** — два нулевых блока подряд; один нулевой
   блок, за которым идёт ненулевой заголовок → `bad_tar`; отсутствие конца
   (EOF сразу после последнего тела) допускается как `truncated`-отказ
   только если тело не дочитано, иначе принимается; всё после двух нулевых
   блоков игнорируется (границы проверяются, содержимое не разбирается и не
   считается). **v7 без magic — отказ** (`unsupported_format`, записано
   ограничение). Тела `L,K,x,g` проверяются **до чтения**: ≤ 1 МиБ каждое,
   сумма служебных ≤ 4 МиБ на архив → `meta_too_large`. **Физические заголовки и
   логические записи различаются (правка 3):** `L/K/x/g` — физические блоки,
   входят в **ресурсный** лимит (1 МиБ каждый, 4 МиБ сумма; плюс общий потолок
   физических заголовков `maxEntries + 4096`), но **не** в число логических
   записей `entries`, которое сравнивается с `maxEntries`. Это одно правило для
   сканера и крейта: `scan_mismatch`, если число логических записей, найденных
   сканером, ≠ числу записей, выданных `tar::Archive`.
3. Только после этого служебное тело читается в буфер, не больше проверенного
   размера. PAX разбирается своим ограниченным разбором (`<len> k=v\n`,
   `len` ≤ размер тела, без вложенных записей); ошибка формата —
   `bad_pax`. PAX `size` (и `GNU.sparse.*`) → `pax_size`,
   `unsupported_format`: переопределения размера не принимаются.
   **Записанное ограничение:** файлы > 8 ГиБ принимаются только в формате
   GNU base-256 (поле `size` заголовка); tar с PAX `size` для больших файлов
   отклоняется. Дубликаты считаются по **эффективному имени** (после
   L/PAX-подстановки): точный дубль → `duplicate_name` для всего архива.
   Тесты: корректные PAX `path` и GNU `L` открываются; точный дубль
   эффективного имени (в т. ч. через L против короткого имени) → отказ.
4. Затем `tar::Archive` на том же дескрипторе (вложенные L/K/PAX уже проверены)
   даёт имена/ссылки; расхождение числа записей между сканером и крейтом —
   `scan_mismatch` (отказ).
5. Счётчики: `entries ≤ maxEntries`; `Σ size ≤ maxTotalBytes`;
   `Σ size ≤ maxRatio × file_len` — на этапе `open` по заявленным размерам (для
   TAR сжатие отсутствует, `file_len` ≈ Σ тел, ratio ≈ 1; проверка нужна для
   sparse-подобных подделок).

### 5.2 ZIP (свой разбор до `ZipArchive::new`)

1. EOCD ищется в хвосте `min(file_len, 22 + 65535)` байт; комментарий обязан
   дойти ровно до конца (иначе `bad_eocd`). Если поля EOCD равны `0xFFFF`/
   `0xFFFFFFFF` — ZIP64 locator (ровно 20 байт перед EOCD, сигнатура) и ZIP64
   EOCD по проверенному смещению; усечённый locator → `bad_zip64`.
2. Отказ: номер диска ≠ 0, диск каталога ≠ 0, число записей на диске ≠ общему
   (`multi_volume`); смещение/размер каталога вне файла, `offset + size >
   eocd_pos`, переполнение (`checked_add`) → `bad_range`; число записей
   > `maxEntries` → `too_many_entries` (границы: 100 000 проходят, 100 001 — нет);
   размер каталога > 64 МиБ → `directory_too_large`.
3. Каталог проходится ограниченными чтениями (буфер ≤ 64 КиБ): для каждой
   записи сигнатура `PK\1\2`, длины `name/extra/comment` внутри каталога,
   `local header offset + 30 ≤ cd_offset`, ZIP64 extra разобран, размеры/
   смещения по `u64`; фактическое число = заявленному, иначе `count_mismatch`.
   Имя ≤ 4096 байт (`name_too_long`). Сырые имена пишутся в индекс
   helper-а (HashSet по сырым байтам; ≤ 32 МиБ суммарно) — **точные повторы
   → `duplicate_name` для всего архива** (крейт скрыл бы второй).
4. Только после успеха — `ZipArchive::new` на том же дескрипторе.
   `enclosed_name()` — вторая линия: `None` → запись `refused: "unsafe_name"`.
5. Заявленные размеры суммируются с проверкой `Σ usize ≤ maxTotalBytes`
   (`limit_exceeded`) и по записи `usize ≤ maxRatio × csize` с порогом
   (см. 5.3) — быстрый отказ на этапе `open`.
6. **Локальные записи (правка 4).** Для каждой записи диапазон
   `[local_offset, local_offset + 30 + n + m + csize)` (n, m — длины имени/extra
   **из локального** заголовка, читаются по `pread` 30 + n байт; data descriptor
   учитывается по флагу bit 3) должен лежать до `cd_offset`; диапазоны разных
   записей **не пересекаются** (сортировка по `local_offset`, проверка
   соседних; `overlapping_entries` — защита от zip-quine/«перекрытых» бомб);
   имя в локальном заголовке равно имени в центральном каталоге
   (`local_name_mismatch`). Тесты: пересекающиеся записи, локальная запись
   выходит за `cd_offset`, разные имена → отказ при `open`.
7. Шифрование: помечается `encrypted` (флаг bit 0, AES-extra `0x9901`). Без
   пароля чтение шифрованной записи — `password_required`; ZipCrypto с
   верным 1-байтовым заголовком, но неверным CRC — `bad_password`
   (запись дочитывается и проверяется CRC, как в пробе `compat`).
   Сжатие кроме `Stored`/`Deflate` — `unsupported_compression`.

### 5.3 Реально обработанные байты (при чтении)

Внутренний буфер декодирования 8 КиБ; после каждого буфера обновляются
`out_total`, `in_total`, `out_entry`, `in_entry` (прочитано сжатых байт —
счётчик над `Read`). **Отказ `limit_exceeded` и очистка потока, если:**
1. `out_total > maxTotalBytes` (`total_bytes`);
2. по записи `out_entry > maxRatio × in_entry` при `out_entry ≥ 65 536`
   (`ratio`; льгота 64 КиБ — **только для одной записи**);
3. по архиву `out_total > maxRatio × in_total` при `out_total ≥ 1 МиБ`
   (`ratio`; множество мелких записей льготой не обходится);
4. в конце записи `out_entry ≠` заявленному `usize` (`size_mismatch`);
5. CRC не сошёлся (`crc_mismatch`);
6. данные кончились раньше (`truncated`).

Общий коэффициент проверяется **при `open` по заявленным размерам** и **при
чтении по фактическим байтам до выдачи порции** в `WriteSession` (порция не
отдаётся, пока счётчики не обновлены). Превышение отношения — не более чем
на один буфер: для fixture «ratio 1:1000» записанные байты < 101 × сжатых.
`maxRatio` по умолчанию 100, владелец может поднять; текст отказа: «Архив
сжат сильнее допустимого (коэффициент > N:1); возможно, это архивная бомба.
Поднять предел можно в настройках». Границы-тесты: запись `out_entry` = 65 535
(льгота, отказа нет при ratio > 100) и 65 536 (проверка включается); архив из
10 000 записей по 32 КиБ с ratio 1000 → отказ по общему коэффициенту.

### 5.4 Имена и типы (helper + `archive-guard.ts`)

`checkEntryName(name: Uint8Array | string): NameSegment[] | "refused"` — отказ
для: пустого имени и пустых сегментов (кроме одного завершающего `/`), `..`,
`.` внутри пути, абсолютных (`/…`), дисковых (`C:`, `\\?\…`, UNC),
обратной косой черты (трактуется как разделитель **и** отказ: имя с `\` в
2a — `refused: "backslash"`), NUL, управляющих символов < 0x20,
сегмента > 255 байт, не-UTF-8 имён при распаковке в цель (в списке они
показываются через `name`; распаковка такой записи — `refused: "name_encoding"`).
`RefusedReason`: `unsafe_name | backslash | name_encoding | link_not_supported |
link_escapes | special_file | duplicate_name | name_collision | encrypted_no_password`.
Symlink/hardlink: всегда `link_not_supported`; если цель разрешается за корень
(нормализация по сегментам) — `link_escapes` (точнее, приоритет выше).
Коллизии после нормализации (NFC, регистр на регистронезависимой цели,
`a` файл vs `a/` каталог) — `name_collision` на этапе плана (адаптер, не helper);
запись `x/..` и запись через ранее виденную ссылку невозможны (ссылки не
создаются, `mkdir` планировщика отказывает, если путь существует не как каталог).

## 6. Создание (`pack`)

`{"t":"pack_open","format":"zip"|"tar","staging":pathB64,"zip":{"encryption":"none"|"aes256"}?}` →
`ok{packId}`; для `aes256` перед первой записью — `need_password`/secret.
Staging — приватный файл в серверном каталоге из §7 (`mkdtemp` в `os.tmpdir()`, 0700; файл
создаёт helper `O_EXCL|O_NOFOLLOW`, 0600; путь выдаёт адаптер). Далее:

| `t` | Поля | Ответ |
|---|---|---|
| `pack_add` | `nameB64`, `kind:"file"\|"dir"`, `size` (для file), `mtime`, `mode` | `ok` |
| `pack_data` + data-кадр | `reqId`, байты ≤ 4 МиБ | `ok{written}` (по одному в полёте — окно 1 кадр) |
| `pack_end_entry` | — | `ok` (число записанных байт = `size`, иначе `size_mismatch`) |
| `pack_finish` | — | `ok{size, sha256}` — размер и SHA-256 staging-файла |
| `pack_abort` | — | `ok`; staging удаляется |

Имена записей проверяются тем же `checkEntryName` (на стороне helper и
адаптера); повторы — `duplicate_name`; symlink/special в `pack` — `unsupported`.
Лимиты `pack` те же (`maxEntries`, `maxTotalBytes`). **Источники
`pack` читаются с `expect` по fingerprint из плана** (`read(..., expect)`;
изменение → `changed_since_plan`, `pack_abort`). **Перед созданием staging —
`statfs` каталога staging: свободно ≥ ожидаемый размер (Σ размеров источников,
для ZIP без сжатия) + 64 МиБ, иначе `no_space` до `pack_open`.** ZIP — `Deflate`
(по умолчанию) или `Stored`, ZIP64 при необходимости (`large_file(true)`
по размеру); AES — `AesMode::Aes256`; TAR — `tar::Builder` USTAR, PAX для
длинных имён. Ошибка/отмена → `pack_abort`/выход процесса → staging
удаляется (адаптер дублирует `rm` при падении helper).
Публикация: `archive-writer.ts` читает staging локально (`node:fs`), пишет
через `WriteSession` цели (`openWrite` → `write` → `commit({replace,
expectTarget})`) — то есть `pack` = обычное задание с temp + rename и
`expectTarget` (локальный и SFTP). После commit staging удаляется.
Проверка «pack 3 файлов → list показывает те же имена и размеры» — через
тот же `open`/`list` helper.

  **ровно пять столбцов** `id, source_json, fingerprint_json, created_at,
  last_referenced_at` (порядок и типы как в таблице); `limits_json` отсутствует; ни одно имя столбца не содержит
  `pass`, `secret`, `key`, `token`, `copy`, `temp`, `tmp`, `local`; после
  открытия шифрованного архива с паролем-литералом и создания копии дамп
  строки (`SELECT *`) не содержит ни пароль, ни путь каталога копий

  (строка `archives` не удаляется). Отдельный столбец `archive_id` в `jobs`
  **не вводится**; если он понадобится (медленный разбор) — это новая
  миграция, сначала вопрос координатору. Строка удаляется **только после освобождения последней
  ссылки**: при каждом снятии ссылки (задание перешло в терминальное, панель
  закрыта) `last_referenced_at = now`; очистка (при старте и раз в час)
  удаляет строки **без ссылок и с `last_referenced_at` старше 7 суток**.
  Тест: закрыть панель с ожидающим заданием → закрыть и переоткрыть БД →
  источник восстановлен по UUID (`list`/`open` работают) → задание завершено →
  очистка с часами «+7 суток + 1 с» удаляет строку; «+6 суток» не удаляет;
  панель закрыта, ссылок нет → строка живёт до срока и удаляется после.
  Номера согласуются по очереди слияния срезов (S14 сливается после S13; если
  к началу кода в ветке этапа добавлены другие миграции — стоп и вопрос, не
  перенумеровывать). Тест «в журнале ровно N миграций» (`job-store-sqlite.test.ts`,
  тест журнала SDK) обновляется **в том же коммите**, что и миграции:
  ожидание = число миграций ветки + 2; тест на fixture-БД этапа 1
  (`main@b44884df`) — старые чекпоинты и задания читаются.
- **Источник архива (решение A).** (1) Архив на endpoint **той же машины, что
  сервер плагина** (`host:<id>` совпадает с машиной сервера): без копии, helper
  открывает обходом от корня endpoint (§3), fingerprint сверяется до `open` и
  после каждого запроса — **путь отключён до доказательства `primaryHostId` на
  стенде; сейчас всегда приватная копия** (код пути «без копии» не включается;
  тест: локальный `host:<id>` тоже идёт через копию, `open` получает корень
  каталога копий, а не корень endpoint). (2) **Любой endpoint** (SFTP, host другой
  машины): приватная копия в **серверном приватном каталоге** (см. «Каталог копий и staging» ниже) через `FileProvider.read` с `expect`; **перед копированием —
  одноразовая оценка объёма как в S10** (`estimateId`, привязка к инициатору,
  показывается объём чтения); агенту копия — только с правом `read` на файл
  архива **и** с оценкой (без `estimateId` — `consent_required`). Лимит
  `maxArchiveFileBytes` = 10 ГиБ и `statfs` с запасом; прогресс/отмена — как у
  задания. **Перед каждым запросом к копии** адаптер сверяет fingerprint
  исходного файла на endpoint; изменение → `changed_since_plan`. Копии
  удаляются при закрытии архива, при падении helper и **при старте плагина
  (сироты в каталоге копий без записи в реестре)**.
- **Каталог копий и staging (на машине сервера).** Helper работает на машине
  сервера плагина, поэтому и копии архивов (§7), и staging `pack` (§6) лежат
  там же: адаптер создаёт приватный каталог **конкретной установки**
  `os.tmpdir()/commander-archives-<installId>/` (`installId` — случайный
  идентификатор установки плагина, хранится в настройках плагина) с правами
  **0700**, а в нём на каждый запуск сервера — подкаталог `mkdtemp` с файлом-замком
  `lock` (JSON `{pid, startedAt}`: pid процесса и время старта процесса по
  `ps -o lstart= -p <pid>`; файл пишется `O_EXCL`, 0600, держится до выхода)
  через `node:fs` с правами **0700** (файлы 0600, `O_EXCL|O_NOFOLLOW`).
  `experimental_paths.dataDir` **не используется**: он есть только у хостового
  воркера и может быть на другой машине. **Очистка сирот** при старте — только
  внутри `commander-archives-<installId>/` и только подкаталоги **с замком, чей
  владелец не жив** (процесса с таким `pid` нет **или** время старта процесса
  не совпадает с записанным — защита от переиспользования pid); подкаталог без
  замка или с нечитаемым замком не удаляется, а помечается в журнале кодов.
  **Соседний активный экземпляр под тем же UID не трогается**; другие
  каталоги `os.tmpdir()`, каталоги других установок и пользователей не
  трогаются (проверка владельца `uid`, `lstat` без следования по ссылкам,
  удаление без `follow`). **Если `ps` недоступен (нет файла, ошибка, таймаут 2 с) или вывод не разобран
  — замок считается живым, ничего не удаляется** (тест: поддельный `ps` с
  мусором/ошибкой → подкаталоги целы). Тест: два экземпляра (активный сосед с живым pid и
  замком + подкаталог мёртвого владельца) — удалён только мёртвый; подкаталог без
  замка остаётся; pid жив, но время старта другое → удаляется. **Отпечаток для
  `open.expect` (`dev, ino, size, mtime`) адаптер берёт из собственного `lstat`
  копии** (для не-копии — из `lstat` исходного локального файла); у
  `FileProvider` `dev`/`ino` нет (`Fingerprint` = `size`+`mtimeNs`), поэтому
  провайдерский отпечаток служит только сверке источника на endpoint.
- **Права (решение B).** Чтение `archive:<uuid>` = право `read` на исходный ref
  архива (владелец и агент); распаковка = `copy` из `archive:` в цель — права
  как у `copy` (`read` источника, `write` цели). Реестр хранит исходный ref
  и проверяет grant при каждом запросе, а не при открытии.
- `ArchiveProvider implements FileProvider` (`capabilities: {}`): `list` →
  `list`, `stat` → `stat`, `read(path, offset, length, expect)` → `read_open`
  (с кэшем одного текущего потока) + `read`; `expect` сверяется с
  fingerprint записи; `openWrite/mkdir/rename/remove/copyWithin/sha256` —
  `CommanderError("unsupported")`. Fingerprint записи: `{size, mtimeNs}`
  из архива; fingerprint самого архива проверяется в helper (`verify`) при
  каждом чтении — смена файла = `changed_since_plan`.
- Распаковка: `buildPlan` с источником `archive:` — обычный `copy` на
  каждый файл, `mkdir` на каталоги. Для плана helper-ом уже проверены лимиты
  (`open`); `archive-guard.ts` строит для плана: элементы `refused`
  (§5.4), счёт записей/байт (`limit_exceeded` при плане для 100 001),
  коллизии. Байты тела при выполнении считает helper (§5.3): превышение —
  элемент `failed limit_exceeded`, temp удаляется раннером (stage-1).
- Пароль: RPC `archive.password {archiveId, password}` вызывается **только
  из диалога UI** (владелец); не входит в agent tools и CLI; ответ на
  `password_required` — диалог `needs_password` в строке архива. Агентский
  `commander_*` на зашифрованном архиве получает `password_required`, а не
  запрос пароля.
- Права `pack`: источники `read`, цель `write`.

## 8. Тесты (литеральные; fixtures генерируются в `mkdtemp`)

Генератор fixtures — отдельный тестовый модуль на `node:zlib` (ZIP/TAR
собираются байтами руками; helper их не создаёт). Рассматриваются как
Rust-тесты (`helper/tests`, бинарные fixtures через `cargo test`) **и** TS-тесты
(реальный helper по `HELPER_BIN` или `bin/…`, `describe.skipIf` на не arm64).

Core / guard (vitest, без helper):
- `checkEntryName`: `"../x"`, `"/abs"`, `"C:\\x"`, `"a/../../b"`, `"a\\b"`, `"a//b"`,
  `"a\0b"` → `"refused"`; `"a/b/"` → `["a","b"]`.
- 100 001 записей в индексе → `limit_exceeded` при плане; 100 000 проходит.
- symlink внутри цели и снаружи → `link_not_supported`/`link_escapes`.
- пересечение имён после NFC/регистра → `name_collision`.

Интеграция с helper (`open` и чтение):
1. TAR `L`, `K`, `x`, `g` с заявленным телом 256 МиБ → `meta_too_large`, helper
   прочитал ≤ 512 + 512 байт (счётчик через `pread`-обёртку; тест в Rust
   проверяет число прочитанных байт; отдельный процесс, пик RSS ≤ 32 МиБ).
2. Служебная запись ровно 1 048 576 → читается; 1 048 577 → `meta_too_large`;
   цепочка служебных суммой 4 МиБ + 1 → `meta_too_large`; `bad_pax`; PAX `size`
   → `pax_size`; усечение → `truncated`; base-256 переполнение →
   `size_overflow`.
3. ZIP/ZIP64: 100 001 записей, каталог 64 МиБ + 1, диапазон за файлом, диск ≠ 0,
   count_mismatch, усечённый ZIP64 locator → отказ **до** `ZipArchive::new`
   (в Rust — счётчик/хук, что конструктор не вызван); 100 000 — проходит.
4. Бомба ZIP 1:1000 → `limit_exceeded`, записано < 101 × сжатых; TAR/ZIP сверх
   `maxTotalBytes`, усечённое тело, `size_mismatch`, `crc_mismatch` → отказ, ничего
   не опубликовано.
5. `../x`, `/abs`, `C:\x`, `a\b`, symlink/hardlink наружу, два одинаковых имени
   (`duplicate_name` для всего архива), запись через ссылку — каталог цели и
   внешний файл (с заранее известным содержимым) не изменены.
6. Пароль: верный/неверный, ZipCrypto с «счастливым» заголовком (литерал из
   пробы `compat`), CP437 `café.txt`/сырые `caf\x82.txt`; пароль не встречается
   в argv, stderr, ответах и дампе трафика (тест ищет литерал-пароль).
7. Целостность: файл подмен SHA / нет `SHA256SUMS` / symlink — `helper_checksum_failed`,
   процесс не запущен (счётчик spawn = 0); `--version` совпадает с `package.json`.
8. Архив изменён на диске между `open` и `read` → `changed_since_plan`.
9. Pack: 3 файла → ZIP и TAR → `open`+`list`: те же имена и размеры; AES — без
   пароля `password_required`; прерывание → staging удалён.
10. Миграция: строки заданий этапа 1 (fixture БД `main@b44884df`) читаются.
11. Платформа: `process.platform !== "darwin"` → `archives_unavailable`,
    helper не запускается.
12. Завершение: отмена и выгрузка → процесс завершён (проверка по pid), потоки закрыты.

Добавлено ревью (A–H, правки 1–7):

## 9. Решения и остаточные вопросы

Решено координатором: файлы сверх плана мои (бинарь в git по ADR 0002;
`package.json` правит и S18 — слияние по очереди); `.tar.gz/.tgz` не делать;
точные дубли имён — отказ всего архива с понятным текстом (§10); ссылки при
распаковке всегда отклоняются; льгота 64 КиБ — только для одной записи плюс
общий коэффициент (§5.3); коды ошибок — `ErrorCode += invalid_archive` и
необязательный `reason` с проверкой пары `code`+`reason` (§10); `errors.ts`,
`errors.test.ts` — во владении S14; класс RPC `invalid_archive` → `invalid`.

Остаются:
1. `Checkpoint.commitIntent`: колонка `commit_intent_json` разрешена координатором (§11); миграция append-only, **8-я, индекс 7** в `MIGRATIONS` (сейчас в ветке этапа `MIGRATIONS.length = 7`, 7-я — `scan_jobs` из S10). Если к началу кода в ветке этапа появятся другие миграции — **стоп и вопрос**, не перенумеровывать. S14 сливается после S13.
2. Признак «host — машина сервера» (§3): флага нет, `primaryHostId` не доказан; до доказательства на стенде всегда приватная копия.
3. Пароль живёт только в helper; при рестарте плагина/helper вводится заново.
4. Сборка helper: `cargo` есть локально (rustc 1.97); бинарник коммитится как
   у Remote Hub, подпись ad-hoc; карантин на чистой машине — до релиза.
5. Изменение существующего ZIP/TAR — `unsupported`.
6. `RLIMIT_AS` не считаем гарантией (§3); результат теста — в спецификацию.
7. `invalid_archive` затрагивает потребителей `ErrorCode` (исчерпывающие
   `switch`/таблицы UI, `rpc.ts`): правки только своими блоками; несовместимое
   место вне владения — стоп и вопрос.
8. Мои дополнения к списку подкодов `reason` (§10): `too_many_open_archives`,
   `unsupported_format`, `unsupported_compression`, `archives_unavailable`;
   итого 38.

## 10. Коды ошибок и подкоды (`reason`)

Решение координатора (б). `src/core/errors.ts` и `errors.test.ts` — во
владении S14 для этого блока:
- `ErrorCode` += `"invalid_archive"`;
- `CommanderErrorShape` += необязательное `reason` (`z.enum`, ниже);
  схема проверяет **пару** `code` + `reason` (`superRefine`): недопустимая
  пара не проходит; `reason` допустим только у кодов из таблицы пар, у
  остальных (`no_space`, `changed_since_plan`, `cancelled`, `timeout`,
  `consent_required`, …) любой `reason` не проходит;
- `CommanderError` получает необязательную опцию `reason`; `toShape()` её
  выдаёт (без `reason` ключ не добавляется);
- префиксов в `message` нет нигде; UI выбирает строку по паре `code` +
  `reason`;
- класс RPC (`publicError`, `rpc-handlers.ts`, отдельный блок S14):
  `invalid_archive` → `invalid`; остальные — по существующей таблице
  (`auth_failed`, `unsupported`, `limit_exceeded`, `internal` → `invalid`;
  `changed_since_plan` → `conflict`). `publicError` отдаёт `toShape()` в
  JSON, поэтому `reason` доходит до UI без изменений кода маршалинга.

Допустимые пары:

| `code` | допустимые `reason` |
|---|---|
| `invalid_archive` | `bad_tar, bad_zip, bad_eocd, bad_zip64, bad_range, bad_pax, count_mismatch, scan_mismatch, overlapping_entries, local_name_mismatch, multi_volume, truncated, size_overflow, duplicate_name, crc_mismatch, size_mismatch, aes_auth_failed` (повреждённые данные — не `internal`) |
| `limit_exceeded` | `meta_too_large, directory_too_large, too_many_entries, name_too_long, ratio, total_bytes, too_many_open_archives` (последний — добавлен мной: слот helper-процессов) |
| `auth_failed` | `password_required, bad_password` |
| `unsupported` | `link_not_supported, link_escapes, encryption_unsupported, v7_tar, pax_size, unsupported_format, unsupported_compression, archives_unavailable` (три последних и `unsupported_format` добавлены мной: sparse/нестандартные типы, методы сжатия кроме Stored/Deflate, нет helper для платформы) |
| `internal` | `helper_checksum_failed, helper_version_mismatch, helper_crashed, protocol_error` |

Итого 38 подкодов (17 + 7 + 2 + 8 + 4). `link_not_supported`/`link_escapes` — `reason` ошибки,
когда операция над самой ссылкой запрошена напрямую (`read` ссылки через
`ArchiveProvider`); при пакетной распаковке те же причины — поле элемента
плана (`RefusedReason`, ниже), не ошибка.

AES, шифрование TAR.

Строки по парам (RU), класс RPC, что видит агент (всегда `code`, `reason`,

**Тесты (литералы):**
- строка задания этапа 1 (`job.error` без `reason`, fixture `main@b44884df`)

## 11. Падение helper, рестарт, публикация

**Падение (решение E).** EOF, сигнал, обрыв посреди кадра, выход без `close`:
ожидающий запрос завершается `helper_crashed` (`internal`, retryable);
элемент задания — `failed`; temp убирает раннер (stage-1 `abort()`); слот и
копии (§7) освобождаются; адаптер **ждёт выхода процесса** после SIGKILL.
Следующий запрос перезапускает helper, повторяет `open` и сверку fingerprint;
для шифрованного архива снова просит пароль (`password_required`).
Лимит — 3 перезапуска за 5 минут на архив; дальше `archives_unavailable` до
повторного открытия архива владельцем. Тесты: kill -9 посреди `read`; EOF
между data и ok; 4-й рестарт за 5 минут → `archives_unavailable`.

**Рестарт плагина (решение G).** Задание распаковки из шифрованного архива
после рестарта сервера → `password_required` (состояние «ждёт владельца»,
`awaitsOwner`), не `unknown`. Задания из нешифрованных архивов продолжаются
по чекпоинтам stage-1/S17 после повторного `open` и сверки fingerprint.

**Публикация (решение H).** `pack` и распаковка публикуют через
`WriteSession`; исходы различаются так:
1. **Сбой до публикации, исход известен** (локальная ошибка чтения,
   `read_finish`, падение helper до `commit`, `write` вернул подтверждённый
   отказ) → элемент `failed`, `abort()`, ничего не опубликовано.
2. **Подтверждённый отказ `commit`** (`changed_since_plan`/`already_exists`/
   `no_space`) → конфликт/ошибка, `abort()`.
3. **`write` вернул `outcome_unknown` от провайдера** (провайдер сам
   отдаёт его для неоднозначных изменений, S5: потерянный ответ **после**
   отправки) → задание `outcome_unknown` с чекпоинтом (temp мог измениться):
   `abort()` вслепую **не вызывается**, temp остаётся для сверки по
   `tempFingerprint` (reconcile stage-1). `connection_failed` по S5 означает
   «не отправлено» — обычный `failed` с `abort()`; `timeout` не
   переклассифицируется раннером (§ ниже, «Коды раннера не меняются»).
4. **Потеря ответа на `commit`** (обрыв/таймаут после отправки) →
   `outcome_unknown`; публикацию доказывает чекпоинт, записанный **до**
   отправки `commit`.

**Доказательство публикации и правка раннера.** Сейчас `job-runner.ts:1078`
вызывает `session.commit(...)`, а `committed` пишется после возврата
(`:1091`). **Правка (решено координатором):** в `Checkpoint` добавляется
необязательное `commitIntent?: { size: string, sha256: string, tempFingerprint:
Fingerprint }` — **без других полей** (`targetPath`, `expectTarget` уже есть в чекпоинте).
**Хранение в SQLite (факты кода).** Чекпоинт собирается **по колонкам**
(`job-store-sqlite.ts`: `writeCheckpoint` `:242`, `lastCheckpoint` `:399`;
колонки `temp_fingerprint_json`, `cleanup_json` и т. д.); общей JSON-колонки
«всего чекпоинта» **нет**. Поэтому «внутри существующего JSON» невозможно без
новой колонки. **Решено координатором (окончательно):** миграция с **одной** новой
необязательной колонкой `commit_intent_json TEXT` (`ALTER TABLE checkpoints
ADD COLUMN`, **миграция № 8 (индекс 7 в `MIGRATIONS`, после `scan_jobs`)**, как `cleanup_json` в `migrations.ts:45`), без перезаписи старых
строк. Формат: старые строки — `NULL` (поле отсутствует, читается как раньше);
новые — `JSON.stringify({size, sha256, tempFingerprint})`, разбор схемой
`CommitIntent` (zod, `strict`); повреждённый JSON → ошибка чтения чекпоинта как
у других колонок. Тесты: миграция на fixture-БД этапа 1 (`main@b44884df`) —
старые чекпоинты читаются без поля; **запись → закрытие БД → открытие →
`commitIntent` на месте**; повторная запись без поля обнуляет колонку.
Раннер (блок S14 в `job-runner.ts`) пишет его непосредственно **до**
`session.commit` — **только для заданий с источником `archive:` и для `pack`**
(обобщение на остальные задания — позже). Старый чекпоинт без поля читается
как раньше (тест на фикстуре чекпоинта этапа 1 `main@b44884df`, не только
`job.error`).

**Сверка после потери ответа на `commit` (reconcile):**
- `done` **только** при совпадении SHA-256 содержимого **цели** с
  `commitIntent.sha256`; размер + mtime недостаточны; если SHA-256 цели
  прочитать нельзя (нет права, обрыв, провайдер) → `unknown`. Тест: цель с тем
  же размером и mtime, но другими байтами → `unknown`.
- Повторная публикация после рестарта — **только** при одновременном
  выполнении: temp подтверждён (совпал с `commitIntent.tempFingerprint` **и**
  SHA-256 temp равен `commitIntent.sha256`); цель совпадает с исходным
  `expectTarget` (отсутствует либо прежний отпечаток); для замены — разрешение
  доказано; у провайдера есть `atomicReplace`. Иначе `unknown` без `rename`.
  Прежняя `WriteSession` утрачена, а `openWrite` эксклюзивен, поэтому
  проверенный temp публикуется **не через `session.commit`**, а
  `provider.rename(tempPath, targetPath, …)`. Ветки:
  1. **Цели нет** (`expectTarget === "absent"`) → `rename(temp, target,
     { replace: false, expectTarget: "absent" })`; результат сверяется
     SHA-256 цели → `done`.
  2. **Цель существует** (`expectTarget` — отпечаток; в том числе когда «цель и
     temp существуют») — это ветка **разрешённой замены**, не безусловный
     `unknown`. Поля `item.replace` в `PlanItem`/`Checkpoint` **нет**;
     разрешение после рестарта доказывает **только** `plan.conflictPolicy`:
     `overwrite` — само по себе; `overwriteIfNewer` — **не само по себе**
     (раннер при неизвестном `mtimeNs` спрашивает владельца, при равном или
     более новом назначении пропускает, `job-runner.ts:932`): нужно
     **доказательство по сохранённым отпечаткам плана**, что источник строго
     новее цели, — `item.fingerprint.mtimeNs` и `item.expectTarget.mtimeNs`
     оба известны и `BigInt(источник) > BigInt(цель)`; иначе `unknown`,
     `rename` = 0 вызовов. Решения владельца по конфликтам хранятся
     лишь в памяти раннера (`job-runner.ts:105`, `Map decisions`) и в БД не
     попадают, поэтому при политике `ask`/`skip`/`rename` → `unknown`.
     При выполнении всех условий → `rename(temp, target, { replace: true,
     expectTarget: исходный })`, затем SHA-256 цели → `done`.
  `atomicReplace` требуется **только для ветки 2 (замена)**; ветка 1
     (публикация в отсутствующую цель, `replace:false`, `expectTarget:
     "absent"`) его **не требует** (положительный тест с `posixRename: false`,
     подтверждённым temp и `absent` → `rename`, `done`).
  3. Нет `atomicReplace` в ветке замены (SFTP без posix-rename), разрешение не доказано,
     цель не совпала с `expectTarget` или любое иное условие неизвестно →
     `unknown`, решает владелец.
  Тесты (по одному на каждый пункт): пересоздать провайдера (новый экземпляр,
  пустая таблица сессий) → ветка 1 с `{replace:false, expectTarget:"absent"}`,
  `openWrite` не вызван, `done`; ветка 2 при `conflictPolicy: "overwrite"`;
  при `overwriteIfNewer` и известных `mtimeNs` источника строго новее цели →
  rename с `replace:true`, `done`; `overwriteIfNewer` при равном/более старом
  источнике или неизвестном `mtimeNs` → `unknown`, rename = 0; ветка 1 на
  SFTP-моке `posixRename: false` → rename, `done`; политика `ask` после
  решения владельца `overwrite` (решение утрачено при рестарте) → `unknown`; **отсутствие каждого условия** по
  отдельности (temp изменён; SHA-256 temp другой; цель не совпала с
  `expectTarget`; политика `ask`/`skip`/`rename`; нет `atomicReplace` — SFTP-мок с
  `posixRename: false`) → `unknown`, `rename` не вызван.
- Любой другой исход (цель другого вида, цель и temp на месте, сверка
  недоступна) → `unknown`, решает владелец.

**Коды раннера не меняются:** сопоставления `connection_failed`/`timeout` →
`outcome_unknown` в раннере нет (это изменило бы все SFTP-задания и
противоречит S5). Раннер опирается на `outcome_unknown`, который провайдер сам
отдаёт для неоднозначных изменений (`connection_failed` = запрос не
отправлен). Иная семантика `timeout` при `write` — отдельная правка S5, не в
этом срезе; записано как известное ограничение.

Тесты: SFTP-мок, у которого `write` теряет ответ после применения и отдаёт
`outcome_unknown` → temp не удалён; **ответ на `commit` потерян после rename** →
SHA-256 цели совпал → `done`, второй `commit` не вызван (счётчик = 1); цель того
же размера и mtime с другими байтами → `unknown`; цели нет, temp совпал по
отпечатку и SHA-256 → один повторный commit; temp изменён → `unknown`;
чекпоинт без `commitIntent` читается.

## 12. Что выяснено и отклонено при реализации (код)

Факты проверок на macOS arm64 (Darwin 27, rustc 1.97) и решения, принятые по ходу:

- **`RLIMIT_AS` не применяется:** `setrlimit` отказывает, helper сообщает `hello.rlimit_as: "failed"`. Защита —
  ограниченные буферы, `RLIMIT_CPU` на запрос, таймаут 30 с и сторож RSS 512 МиБ в адаптере (§3).
- **Открытие файла:** на macOS `O_NOFOLLOW` вместе с `O_NOFOLLOW_ANY` даёт `EINVAL`; helper использует один
  `O_NOFOLLOW_ANY` (он запрещает ссылку в любом компоненте). Корень в `open` обязан быть канонизирован
  (`realpath`): адаптер передаёт `realpath` каталога копии.
- **SDK 0.6.132:** у `hosts.list()` нет признака «машина сервера»; путь без копии не включён вообще — любой архив
  сначала копируется в приватный каталог сервера (§7). `experimental_spawnHostProcess` запускает helper;
  каталог плагина — `bb.sdk.plugins.list()` → `rootDir`.
- **Кадры:** `list` принимает поле `prefix` (base64 сырых байт); у синтетического каталога `id: null`; числа u64
  в ответах — десятичные строки; запись `ArchiveEntry` может нести `refused` (отказ helper-а).
- **Пароль:** helper обязан получить кадр `0x03` на каждый `need_password`. «Нет пароля» адаптер отвечает
  однобайтовым заполнителем (NUL), результат сообщает как `auth_failed`+`password_required`. Пароль владельца,
  введённый позже, принимается тем же процессом.
- **TAR:** при создании длинные имена пишутся GNU `L`; GNU `L` с несколькими завершающими NUL отклоняется как
  `scan_mismatch` (крейт `tar` читает такое имя иначе).
- **Зависимости helper:** к списку добавлен `sha2` 0.10.9 (SHA-256 staging-файла); `flate2` — dev-зависимость тестов
  и транзитивная `zip`. Полный список — в корневом `THIRD_PARTY_NOTICES.md`.
- **Поле `files` в `package.json` не добавлялось:** у пакета его нет, `bin/` входит в сборку без него.
- **Отказанные записи** показываются в списке как `other`/`symlink`, никогда как `file`/`dir`; чтение такой записи
  — `unsupported` (`link_not_supported`/`link_escapes`) либо `invalid_path`/`invalid_name`.

### Не сделано в этой ревизии кода (остаётся срезу)

- Вид плана `pack`: схема модели и права есть (`OperationKind += pack`, `REQUIRED.pack`), но планировщик и
  раннер для `pack` не реализованы; готовы `packToStaging` и `publishStaging` (`archive-writer.ts`) с тестами на
  настоящем helper (ZIP, TAR, AES-256).
- Права агента к `archive:` (tools/CLI): доступ агента к архивам не открыт (RPC только для клиента-владельца).
- Одноразовая оценка объёма копии (`estimateId`) для агента — ждёт открытия доступа агенту.
- Лимиты `ExtractLimits` проверяются helper-ом при `open` (`too_many_entries`, `total_bytes`, `ratio`); план-уровневая
  проверка `checkExtractLimits` в планировщике не подключена.
- Снимки интерфейса 1440×900 и 768×900 не сделаны.
- Изменение существующего архива — `unsupported` (как в §1).

## 13. Деление на S14a и S14b (решение координатора)

**S14a (этот срез):** чтение и распаковка. Дополнительно к §12 сделано:

- **estimateId для копии** (S10-образец). Архив на SFTP или на `host:` не той машины (`primaryHostId` из
  `bb.sdk.system.config()`; не определился — значит «не та») копируется на сервер только после одноразовой
  оценки: `archive_open {estimateOnly: true}` возвращает `{estimateId, bytesPlanned}` без чтения файла;
  `archive_open {estimateId}` открывает. Идентификатор привязан к владельцу, `ResourceRef` и версии файла
  (`size`+`mtimeNs`), живёт 10 минут, расходуется при первом использовании, пул 32. Без него копия не
  начинается (`op:read` = 0). UI показывает «будет прочитано N» и кнопку «Копировать и открыть».
- **Агент и `archive:` закрыты.** Никакой грант, включая `"*"`, не покрывает `archive:`; `dir_list`/`entry_stat`/
  `file_read` отвечают тем же отказом «Path is outside the agent's grant», планирование — «Commander planning
  failed outside the metadata grant». `archive_open` и пароль — только клиент-владелец. Откроется в S14b.
- **`pack` отложен до S14b и отказывается как `unsupported`:** `buildPlan` и `JobRunner.submit` отвечают
  «Creating archives is not available yet». Модель (`OperationKind.pack`), права и `archive-writer.ts` остаются;
  писатель не подключён ни к RPC, ни к UI (в продуктовом коде на него ссылок нет, только тесты).
- **Тест миграций на данных этапа 1:** `src/adapters/bb/testing/fixtures/stage1-b44884df.sqlite` — БД, записанная
  кодом `main@b44884df` (6 миграций, выполняющееся задание и чекпоинт `copying`); `stage1-fixture.test.ts` применяет
  к ней текущие миграции 8 и 9, проверяет, что журнал 0–5 не изменился и что задание и чекпоинт читаются.
- **Строки ошибок по паре `code`+`reason`** (`src/ui/archive-text.ts`): в UI показываются только они, а не текст
  host-а; тест полноты на все 38 пар.
- **Снимки** 1440×900 и 768×900 (архив панелью, диалог пароля, отказ `invalid_archive`, оценка копии) — в хранилище
  треда: `$BB_THREAD_STORAGE/s14a-snap/`. Это отрисовка реального `Workspace` собственным стендом (vite + headless
  Chromium) с тёмной темой, похожей на BB; иконки стенда — наборы Lucide из артбордов, часть имён без иконки.
  Боковой панели «Архив» (формат, число записей, коэффициент) из артборда в S14a нет.

**S14b:** планировщик и раннер `pack`, подключение `archive-writer.ts`, доступ агента и CLI к архивам
(право `read` на исходный ref, оценка копии для агента), панель сведений об архиве.

### Правки по ревью S14a

- **Своя машина не определяется:** оценка нужна для любого источника, включая `primaryHostId`; `isDirectEndpoint`
  удалён. Доказательство одинаковости машины (файл-метка, `dev`/`ino`) — позже, не в S14a.
- **Отпечаток из оценки доходит до копирования:** `manager.open/resume(..., {expect})` сверяет его (и сохранённый
  при `resume`) с `stat` до первого `read`; расхождение — `changed_since_plan`, UI: «Файл изменился — оцените снова».
- **Холодный `archive:<id>`:** `endpoints.prepare` и `provider` отвечают `consent_required` («нужна новая оценка») и
  ничего не копируют; для неизвестного id — `not_found`. RPC `archive_resume {archiveId, estimateOnly | estimateId}`
  берёт сохранённый source из реестра, готовит его endpoint и открывает архив под прежним id. Оценка привязана к
  `archiveId`. UI: вкладка с ошибкой `consent_required` на `archive:` один раз сама запрашивает оценку. Задания
  восстановления получают тот же отказ по элементу (`prepareRecovery` его не глотает: он возвращается при первом
  обращении к провайдеру).
- **Клиент helper:** ответы на собственные `cancel` принимаются молча (тест: три отмены подряд); неверный первый
  кадр отклоняет сам `start()` (`protocol_error`); пока ждёт пароль, таймер запроса 30 с заменён ожиданием диалога
  (до 6 минут); буфер кадра `0x03` затирается после записи в stdin.
- **Столкновения имён на цели** отказываются при планировании (`assertNoTargetOverlap`: регистр и NFC на
  регистронезависимой цели) целиком, а не отдельными элементами: в плане нет списка отказанных элементов.
  `findCollisions` остаётся утилитой для S14b.
- **Агент:** `commander_endpoints`/`endpoints_list` не показывают `archive:` и имя архива.
- **Параллельные читатели (пересмотрено):** helper держит до четырёх независимых потоков чтения (`read_open` не
  сбрасывает прежний; пятый — `invalid_path` «Too many open streams»; общий счётчик `total_bytes` считает каждый
  выданный байт один раз). Поток закреплён за читателем записи от первого `read` до `finishRead`; читатель, который
  не продолжает свободный поток (другая запись, окно в другом месте, второй читатель), получает свой; поток
  освобождается при ошибке, отмене и после 30 с простоя, при нехватке места закрывается давно не используемый
  свободный. Две записи, читаемые по очереди, стоят ровно своих размеров (тест на настоящем helper с лимитом,
  равным сумме размеров).
- **helper:** вторая линия `enclosed_name()` реализована, достижимого входа (имя, прошедшее наши проверки, но не
  `enclosed_name`) нет; тесты `misc.rs` без `--features test-hooks` проходят; `ps` — `LC_ALL=C`.
- **Подпись панели:** `label` — имя файла архива, `machine` — машина источника, без служебного слова «server».

### Правки по ревью S14a, раунд 3

- **Барьер подтверждает байты косвенно:** распаковка неизменной приватной копии детерминирована, а сама копия
  защищена отпечатком `expect` и `dev`/`ino` (изменение копии или подмена файла дают `changed_since_open`), поэтому
  `read_finish` (размер и CRC/AES) относится к тем же байтам, что были отданы читателю.
- **Одинаковое имя на цели:** план из архива с двумя элементами, получающими одно имя после NFC (и после
  сворачивания регистра на регистронезависимой цели), отказывается как `invalid_archive` + `name_collision`
  («Два элемента архива получают одинаковое имя в каталоге назначения»); NFC применяется в обоих режимах, на
  регистрозависимой цели `A` и `a` — два файла. Всего 40 допустимых пар (добавлены `name_collision` и
  `consent_required` + `archive_copy` — «Нужно подтверждение копии архива»).
- **Холодный старт приложения:** сохранённая панель `archive:<uuid>` не заменяется домашним каталогом; она сама один
  раз (на каждое обновление панели) запрашивает оценку через `archive_resume`, отмена и ошибка не повторяются, пока
  панель не обновлена.
- **Восстановление заданий:** задание над архивом, чья копия пропала, остаётся `interrupted` с ошибкой
  `consent_required`/`archive_copy` и своим чекпоинтом (не `unknown`); после подтверждённого `archive_resume`
  выполняется новый проход восстановления и работа продолжается с чекпоинта.
- **helper:** ошибка `by_index_raw` при проверке `enclosed_name()` даёт `bad_zip`; достижимого входа нет, покрыто
  юнит-тестом.

### Правки по ревью S14a, раунд 4

- **`total_bytes` по приросту:** helper считает только прирост максимальной достигнутой позиции каждой записи
  (`out_hwm`; `in_hwm` для сжатых). Повторное чтение записи и чтение двумя потоками сразу не расходуют лимит;
  коэффициент по записи, `size_mismatch`, CRC и бомбы без изменений. Сжатые байты считаются оценкой (по заявленному
  размеру и прогрессу), точность та же, что была.
- **Слот потока резервируется до `read_open`**, закрытие не несёт сигнал читателя (четыре отменённых барьера подряд
  не оставляют потоков), пропуск до смещения и первое чтение — одно действие над занятым потоком. Если все четыре
  потока читаются, пятый читатель получает `limit_exceeded` + `too_many_streams` (повторяемо), helper пятого не видит.
  Всего 41 допустимая пара.
- **Задания в ожидании копии:** `pending` без `awaitsOwner` тоже ждёт (не `failed`); после подтверждения ошибка
  `archive_copy` с задания снимается.
- **Очередь:** задание с `consent_required`/`archive_copy` показывает «Нужно подтверждение копии архива» и кнопку
  «Подтвердить копию»; она берёт архив из плана задания и открывает тот же вопрос, даже если вкладка архива закрыта.
  Вопросы выстраиваются в очередь (несколько холодных панелей и заданий), ответ на один не вытесняет другой.
  Заголовок вопроса — «Скопировать архив для открытия».

### Правки по ревью S14a, раунд 5

- **Один вопрос на архив:** пока оценка архива запрошена или её вопрос ждёт ответа, вторая панель, обновление или
  задание про тот же архив не спрашивают снова. После подтверждения перечитываются только панели этого архива, поэтому
  другая холодная панель не получает лишний вопрос.
- **Имя и источник в диалоге:** ответы `archive_open` и `archive_resume` с оценкой несут `source` (endpoint и путь),
  диалог показывает имя файла, подпись endpoint и полный путь.

### Правка по живой приёмке 2a: причина отказа для ссылки

Запись-symlink при распаковке давала элемент задания `unsupported` без `reason`. Теперь исполнитель, встретив в
архиве элемент не-файл и не-каталог, читает его через провайдер архива, и тот отказывает парой из §10:
`unsupported/link_not_supported` (ссылка внутри корня) или `unsupported/link_escapes` (за корнем). Пара идёт
литералами в `job.error`, в элементе задания (`items[i].code`, `items[i].reason`; необязательные поля, пара
проверяется как в `CommanderErrorShape`) и в RPC; очередь показывает строку «имя: текст по паре».
Тест — настоящий helper, ZIP и TAR, обе пары: на диск ничего не записано.

### Правки по ревью симлинк-фикса

- **Цель hardlink считается от корня архива**, цель symlink — от каталога записи (helper `links::classify(name, target, hard)`
  и вторая линия `classifyEntry` в адаптере). TAR hardlink `d/l` → `../x` даёт `link_escapes`.
- **Цель, которую не удалось классифицировать** (ZIP-ссылка длиннее 4096 байт, зашифрованная, нечитаемая, без цели) —
  `link_escapes` (консервативно) в обеих линиях. Граница: 4096 байт внутри корня — `link_not_supported`, 4097 — `link_escapes`.
- Агентский вид заданий и строки очереди при тысячах элементов — S14b.
