# S16 — F4 по серверу

## Редактор и приватные копии

F4 всегда вызывает собственный `slots.fileOpener` с `extensions: []` через
`experimental_openFilePreview({ target: { kind: "host", hostId, path }, location: null, opener })`
с явным ID. Копия создаётся на `primaryHostId` для любого исходного провайдера,
в том числе SFTP и локальной ФС другого BB-хоста. В навигацию передаётся
тот же `hostId`. Если `primaryHostId` отсутствует, F4 сообщает «Хост
редактора BB недоступен» до создания копии и вызова навигации. Успешный
вызов подтверждает принятие навигации.
Доступность редактора подтверждает открывшаяся вкладка после загрузки копии.
При отказе или отсутствии подтверждения Commander показывает сообщение и
действие «Открыть копию в BB» по пути по ADR 0002. Штатный F4 всегда передаёт
явный opener.

Рабочая копия и снимки хранятся в выделенном подкаталоге
`experimental_paths.dataDir` хостового воркера. Host entry адресует файлы по
проверенному UUID сессии и, для снимков, по ревизии. Путь вычисляет адаптер.
Операции открытия проверяют тип файла и используют `O_NOFOLLOW`; сохранение
публикует проверенную временную версию атомарной заменой. Путь от UI не
даёт права на чтение, запись или удаление. Методы host entry принимают
`sessionId` и параметры операции без путей:

- `create` создаёт изолированный каталог копии.
- `readChunk` читает диапазон указанной сохранённой редакции.
- `writeChunk` принимает порцию во временную редакцию.
- `commitRevision` сверяет SHA‑256 и публикует временную редакцию.
- `snapshot` создаёт неизменяемый снимок сохранённой редакции.
- `delete` удаляет рабочую копию или указанный снимок.

Commander скрывает корень копий и его содержимое от всех инициаторов.
Листинг родителя его фильтрует. List/stat/read/search/plan/sync/rename и
операции по их результатам отказывают по тому же контракту, что при выходе
за грант. Поиск, сравнение и рекурсивные планы пропускают вложенный
приватный каталог. Проверка учитывает альтернативные пути к каталогу,
возможные на хосте. Ограничение дополняет защиту `protectedPaths`.
Внутренний доступ заданий S16 ограничен снимками, созданными для этих
заданий. Агент не получает сессии, путей, содержимого и сведений о
заданиях записи владельца.

## Контракт

RPC S16 принимает только `experimental_caller.kind === "client"`.

| Метод | Вход | Результат |
|---|---|---|
| `edit_open` | `{ ref }`, для подтверждённого чтения SFTP также `estimateId` | `{ sessionId, base, opener }`; `opener` содержит ID регистрации и цель навигации |
| `edit_get` | `{ sessionId }` | состояние, номер подтверждённой редакции и метаданные сессии без пути |
| `edit_read` | `{ sessionId, offset, length, revision }`, `length` до 1 МиБ | порция байтов указанной редакции и признак конца |
| `edit_save` | `{ sessionId, baseRevision, offset, bytes, final }`, до 1 МиБ декодированных байтов за вызов; при `final: true` обязателен `sha256` всей редакции | `{ revision }`, номер последней подтверждённой редакции |
| `edit_writeback` | `{ sessionId, clientRequestId, revision, choice?, conflictId? }`, при `choice` обязателен `conflictId` | `{ kind: "written", jobId }` либо `{ kind: "conflict", conflictId, revision, reason: "changed" \| "deleted", current }` |
| `edit_close` | `{ sessionId }` | закрытие сессии |
| `edit_dismiss` | `{ sessionId, conflictId }` | закрытие показанного конфликта и освобождение его снимка |

Порционные RPC редактора требуют живую сессию владельца на том же хосте.
Чтение проверяет номер редакции. Сохранение проверяет `baseRevision` и
принимает порции последовательно с указанными смещениями. Подтверждённая
редакция меняется только после `final` с совпавшим SHA‑256 всей редакции.
При открытии исходная копия становится подтверждённой редакцией 0.
Если загрузка оборвалась до `final`, повтор с тем же `baseRevision`
продолжает загрузку с её смещения либо начинает заново со смещения 0.
Сервер сбрасывает незавершённую загрузку через 10 минут без порций или
при новом `edit_save` с `final` от другой базы. Сброс освобождает место
под временную загрузку. Последняя подтверждённая редакция остаётся
доступной, а новая запись по-прежнему требует актуального `baseRevision`.
После рестарта редактор восстанавливает идентификатор сессии из цели
открытия и проверяет сессию на сервере. У завершённой сессии чтение и
запись отклоняются сообщением
«Сеанс завершён — откройте файл снова». Повторный F4 по тому же оригиналу
возвращает существующую сессию. Инструменты агента для F4 отсутствуют.

Таблица SQLite `edit_sessions` хранит только sessionId, ref, base, hostId,
состояние, created_at и last_saved_at. Та же миграция №10 создаёт
`edit_writebacks` со столбцами sessionId, clientRequestId, revision, jobId,
created_at и отпечатком команды из `revision`, `choice` и `conflictId`.
Ключ — пара (sessionId, clientRequestId). Миграция S16 занимает слот 10.
В ветке этапа пока семь миграций, в ветке S14 к ним добавлены слоты 8 и 9.
Строгая схема Zod проверяет состояние сессии при чтении и записи.
Состояние хранит `conflictId`, показанную версию, включая отсутствие
файла, и связанную редакцию снимка. Квитанция, отпечаток команды и задание
фиксируются одной транзакцией до запуска
очереди. Повтор возвращает прежний jobId, в том числе после потери ответа
или рестарта. Повтор того же ID с другой командой отклоняется.
Содержимое остаётся только на хосте.

## База и подтверждение чтения

Копия читается полностью чанками через `FileProvider.read`. Версия
проверяется по stat перед чтением, ожидаемому отпечатку каждого чанка,
числу принятых байтов и stat после чтения. Несовпадение останавливает
открытие. До создания сессии проверяется весь обычный файл. Принимается
строгий UTF‑8 без NUL и управляющих символов, кроме табуляции, LF и CR,
по правилам S15. Потоковое декодирование переносит незавершённый
многобайтный символ в следующий чанк. Невалидный UTF‑8, включая неполную
последовательность в конце файла, отклоняется сообщением «Файл не
текстовый — правка недоступна». Предел — 16 МиБ. Для большего файла
показывается «Файл слишком большой для правки (до 16 МиБ)».

Для провайдеров с `sha256` база включает размер, mtime и SHA‑256 исходных
байтов. Перед записью используется `checksum` из S10. Для SFTP без
`provider.sha256` база и `expectTarget` содержат размер и mtime. Перед
чтением SFTP владелец видит объём и подтверждает одноразовый `estimateId`
по схеме S10, привязанный к владельцу, ref и показанной версии.

Проверка по метаданным совместима с условиями штатной очереди и
SFTP-адаптера перед заменой. Дополнительное чтение SHA‑256 укрепило бы
предварительную сверку, а финальная проверка SFTP-адаптера по-прежнему
использовала бы метаданные. Остаточный риск — правка того же размера с
тем же серверным mtime, в том числе в пределах одного тика часов. Между
финальной проверкой и удалённым rename остаётся окно.

## Запись и конфликт

«Записать обратно» фиксирует отдельный снимок `rev-N` с SHA‑256 только из
подтверждённой через `final` редакции. Пока идёт сохранение, запрос
отклоняется сообщением «Дождитесь сохранения». Источником плана `copy`
служит снимок, а `fingerprint` плана содержит его SHA‑256. Изменение снимка
даёт `source_changed`. Новые сохранения и повторный F4 не меняют снимок
уже поставленного задания. Штатная очередь переносит через временный файл
и rename. После успешной записи в оригинал база обновляется подтверждённым
отпечатком цели из контрольной точки завершённого переноса с учётом
возможностей провайдера. Последующее чтение цели могло бы принять
чужую правку за результат задания. Для SFTP без `sha256` база берётся из
размера и mtime цели после переноса. Сохранение рядом и задания без
подтверждённой записи оригинала базу не обновляют.

Каждый ответ о конфликте получает `conflictId`, связывающий показанную
версию оригинала с неизменяемым снимком рабочей копии. `revision` запроса
должна совпасть с текущей подтверждённой редакцией и, при выборе в
конфликте, с редакцией связанного снимка. Устаревший идентификатор,
смена версии оригинала или смена редакции копии после показа дают новый
конфликт без постановки задания.

| Состояние или действие | Результат |
|---|---|
| Исходный файл совпадает с базой | `copy` с `expectTarget = base` |
| Оригинал изменён или удалён | Конфликт `changed` или `deleted`, с текущим отпечатком или `null` |
| «Сравнить» | Сохранённая копия и текущий оригинал читаются в режиме просмотра S15; для удалённого показывается отсутствие оригинала |
| `changed`, «Перезаписать» | Сверка с показанной версией, затем `expectTarget` равен её отпечатку |
| `deleted`, «Перезаписать» | Проверка, что файл по-прежнему отсутствует, затем `expectTarget: "absent"` |
| «Сохранить рядом» | Первое свободное `name (2).ext`, `name (3).ext` и далее, `expectTarget: "absent"` |
| Повторное изменение, появление оригинала или занятый выбранный путь | Новый конфликт, рабочая копия сохраняется |
| «Не записывать» | Рабочая копия остаётся в сессии |

Нумерованный соседний файл и явное восстановление удалённого оригинала
соответствуют уточнению координатора после ревью S16. Без явного выбора
удалённый оригинал остаётся отсутствующим.

## Восстановление и очистка

Сессия закрывается после 7 суток с последнего сохранения или, если
сохранений ещё не было, с открытия. Суммарный лимит рабочих копий,
временных редакций и снимков на хосте — 1 ГиБ. Проверка и резервирование
места атомарны для параллельных запросов. Лимит проверяется при открытии,
росте копии, `commitRevision` и `snapshot`. При превышении лимита запрос
отклоняется с сообщением, прежняя редакция остаётся целой и задание не
ставится. Закрытие удаляет рабочую копию, когда её больше не удерживает
живая сессия или незавершённое задание. Снимок удаляется после завершения
его задания, если он не показан в открытом конфликте, в том числе при
живой сессии. Ссылки очереди проверяются по разобранному `plan_json`. При старте после восстановления очереди
проверяются срок сессий и сироты. Ошибка уборки регистрируется без путей,
старт Commander продолжается.

В `server.ts` интеграция помечена `// S16`: подключение контракта host entry и
RPC, восстановление сессий при активации, очистка после восстановления
очереди и завершение работы адаптера при выгрузке. Правила конфликтов и
жизненного цикла находятся в `src/core/edit-session.ts`; операции с
файлами выполняет host-адаптер.

## Проверки

- Неизменный оригинал получает точные байты снимка. SHA‑256 проверяется
  литералом. Изменение оригинала при тех же размере и mtime определяется
  у провайдера с SHA‑256. При конфликте исходные байты остаются прежними.
- Удаление, повторное появление, повторное изменение, перезапись показанной
  версии, нумерация свободного соседнего имени, коллизия после планирования
  и «Не записывать» проверяются отдельными сценариями.
- SFTP без подтверждения и с просроченной или чужой оценкой не читает
  содержимое. Подтверждённое открытие ограничивает фактическое чтение
  оценённой версией. Проверяются также предел размера и смена версии при
  порционном чтении.
- Агент с read на корень не видит копию в list/search, прямое чтение
  отклоняется. Владелец не видит копию в панели. RPC сессий отклоняет
  агентского и plugin-вызывающего, включая запрос с известным sessionId.
- Повторный F4 возвращает существующую сессию. При отсутствии
  `primaryHostId` копия и вкладка не создаются. Потеря ответа → рестарт →
  повтор того же `clientRequestId` возвращает прежний jobId, в очереди
  остаётся одно задание. Повтор того же ID после рестарта с изменённой
  редакцией, действием или идентификатором конфликта отклоняется.
- `edit_read` и `edit_save` отклоняют вызовы агента, плагина и вызовы к
  завершённой сессии. Проверяются превышение размера порции, смещения,
  устаревшая редакция и несовпадение SHA‑256 финальной порции.
- Вкладка B получает конфликт, вкладка C получает другой конфликт после
  изменения оригинала. Выбор B даёт новый конфликт и не ставит задание.
- Вкладка B получает конфликт для rev-1. Вкладка C сохраняет rev-2 без
  изменения оригинала. «Перезаписать» из вкладки B даёт новый конфликт и
  не ставит задание.
- UTF‑8-символ на границе чанков проходит проверку и сохраняет байты.
  Невалидный UTF‑8, обрыв последовательности на EOF, NUL и запрещённый
  управляющий символ отклоняются до открытия сессии.
- Writeback во время сохранения получает «Дождитесь сохранения».
  Следующая правка после успешной записи оригинала использует обновлённую
  базу и не конфликтует с результатом предыдущей записи.
- Закрытие вкладки после первой порции сохраняет подтверждённую редакцию.
  Повтор с той же базой продолжает загрузку или начинает заново.
  Через 10 минут без порций либо при финальной записи с другой базой
  незавершённая загрузка освобождает квоту.
- После пяти последовательных завершённых записей в живой сессии остаётся
  не более двух снимков. Сохранение сверх квоты сохраняет прежнюю редакцию.
  Параллельные операции не превышают квоту и при отказе не ставят задание.
- Закрытие удаляет рабочую копию. Активное задание сохраняет снимок при
  закрытии. Незавершённое задание после рестарта находит прежний снимок.
  Старт удаляет сирот с учётом срока и удержаний.
- На изолированном BB 0.50.1 проверяются локальный файл и SFTP-мок,
  сохранение копии, запись оригинала и конфликт. Снимки 1440×900.

## Детали реализации

- Дополнительные внутренние host RPC разрешают повторное открытие вкладки,
  читают отпечаток снимка и очищают файлы по списку удержаний. Удалённые
  версии и их абсолютные пути в ответ `edit_get` не входят.
- Проверка приватного дерева выполняется на хосте до штатных операций с
  путём. Листинг фильтрует записи до расчёта курсора. Такой порядок
  распространяет ограничение на обходы поиска, сравнения и планирования
  через существующий FileProvider.
- После подтверждённого завершения задания снимок освобождается. Состояние
  `unknown` ещё удерживает снимок для сверки. Чтобы повторить завершившуюся
  неудачей запись после очистки, владелец снова запускает запись текущей
  редакции из сеанса F4.
