# BB Commander — этап 2: дизайн

Статус: утверждён владельцем 2026-11-27.
Основа: ТЗ §5, §6, §11 «Этап 2», «Сквозные проверки»; ADR 0001; срезы S0–S8.

## Зачем

Этап 1 доказал ядро: план → задание → очередь → конфликт, local и SFTP,
человек и агент через одни права. Этап 2 делает Commander рабочим
инструментом на каждый день: найти, сравнить, синхронизировать, разобрать
архив, переименовать пачку, посмотреть и поправить файл на сервере — и
подключить остальные хранилища. Владелец выбрал все четыре группы
сценариев и все провайдеры.

## Цели

- Все сценарии ТЗ §11 «Этап 2» на local и SFTP, приняты вживую на
  изолированном BB.
- Каждый сетевой протокол — отдельная строка готовности со своей матрицей
  (чтение, запись, move, метаданные, возобновление, платформы).
- Всё, что умеет человек, доступно агенту теми же правами и планами
  (tools и CLI), а опасное — через подтверждение владельца.

## Не цели

- Расширения своего формата и TC-плагины (этапы 3–4).
- 7z/RAR на запись. Для них только аудит; чтение — если аудит найдёт
  проверенную библиотеку с подходящей лицензией.
- Своё облачное хранилище секретов: профили и секреты остаются в Remote
  Hub; для S3/WebDAV/SMB/FTP — тот же принцип credential reference (см. 2b).

## Анти-цели (провал, даже если «работает»)

- Синхронизация удалила файлы, которые человек явно не выбрал.
- Распаковка записала за пределы целевого каталога или забила диск.
- F4 молча перезаписал файл, изменённый на сервере после открытия.
- Поиск по содержимому без ведома скачал удалённое дерево.
- HTML/SVG из просмотра исполнился в origin BB.
- Протокол объявлен готовым по моку.

## Подходы (выбрано владельцем)

| Вопрос | Варианты | Выбор |
|---|---|---|
| Разбивка | 2a+2b; одна большая с двумя дорожками; мини-релизы по группам | **2a и 2b** — две приёмки и два релиза |
| Где тяжёлый I/O (архивы, хеши, поиск по содержимому) | JS в сервере плагина; Rust-helper; решить аудитом | **решит аудит S9**, итог в ADR 0002 |
| Одинаковость файлов в синхронизации | размер+время, хеш по выбору; всегда хеш | **размер+время, хеш по галочке** с показом объёма чтения |
| F4 по серверу | редактор BB + кнопка «Записать обратно»; свой редактор; слежение за копией | **редактор BB + кнопка** |
| Содержимое файлов для агента | только метаданные; отдельное право; входит в чтение | **входит в право чтения** — с лимитом размера; `security.md` правится в S9 |
| Секреты S3/WebDAV/SMB/FTP | Credential Vault напрямую; расширить Remote Hub; ADR позже | **Credential Vault напрямую**: профили в Commander, секрет — ссылкой |
| Дизайн новых экранов | один проход `/pd`; по срезу; без макетов | **один проход `/pd` сразу** для всех экранов 2a, параллельно с волной 1 |

## Этап 2a — файловые сценарии (local + SFTP)

| Срез | Что | Ключевые правила |
|---|---|---|
| S9 Аудит и ADR 0002 | библиотеки ZIP/TAR, хеши, diff; JS vs Rust-helper | чтение/запись/шифрование/изменение архива — раздельно; лицензии в THIRD_PARTY_NOTICES; замеры на fixtures |
| S10 Хеши и сравнение | SHA-256 как задание; сравнение файлов и каталогов | прогресс, отмена; для remote показ объёма чтения до старта |
| S11 Поиск и виртуальная панель | имя, маска, метаданные, содержимое; результат — источник `search:` | remote: оценка обхода, лимиты глубины/числа/байт, отмена; содержимое на remote — только явный opt-in |
| S12 Массовое переименование | шаблоны, счётчики, регистр, regex | preview до запуска; regex с лимитом времени/защитой от backtracking; конфликты имён внутри пачки; одно задание |
| S13 План синхронизации | направления, правила, отличия | удаление — только отдельный явный выбор по каждому набору; перед выполнением повторная сверка; план подтверждается |
| S14 Архивы как источник | просмотр, распаковка, создание ZIP/TAR | лимиты размера/числа/коэффициента сжатия; запрет `..`, абсолютных путей и symlink-выхода; пароль через безопасный запрос; изменение архива — temp+rename |
| S15 Просмотр (F3) | текст, hex, код, изображения | через `experimental_openFilePreview` или своя панель; активное содержимое — без исполнения в origin BB |
| S16 F4 по серверу | версия → копия → редактор BB → «Записать обратно» | перед записью сверка хеша+mtime оригинала; конфликт: сравнить / перезаписать / сохранить рядом; temp+rename |
| S17 Восстановление очереди | повтор, возобновление, сверка неизвестного исхода | повтор после неоднозначного RPC не дублирует запись |
| S18 Нагрузка и сквозные проверки | fixtures, память, время первой отрисовки | цели выбрать по исходному замеру до оптимизации; сквозной список ТЗ |

Волны: 1 — S9, S10, S12, S15, S17; 2 — S11, S13, S14; 3 — S16, S18.
Агентам — новые tools/CLI для каждого сценария поверх тех же планов.
UI каждого среза — через `/pd` в выбранном направлении v2.

## Этап 2b — провайдеры

Порядок: BB-хосты (без новых секретов) → S3-совместимые → WebDAV →
SMB → FTP/FTPS. Каждый — срез: матрица возможностей, проверка TLS или
ключей хоста, стенд (Docker: MinIO, WebDAV-сервер, Samba, vsftpd), отказы.
FTP без шифрования — предупреждение и opt-in. Профили этих протоколов —
в Commander, секреты — ссылкой в `makosh-credential-vault` (решение
владельца); первый срез 2b сверяет контракт Credential Vault и пишет ADR.

## Решения координатора (проверьте)

- **Remote через существующий контракт.** Хеши, сравнение, поиск по
  содержимому и F4 на SFTP читают поток через `hub_sftp_op read` Remote Hub;
  правок в Remote Hub для 2a не нужно. Хеш на стороне сервера не
  используется. Перед стартом показывается объём чтения.
- **S9 блокирует только S14 и поиск по содержимому.** Хеши (S10) — на
  встроенном `crypto`, просмотр (S15) — без архивов; волна 1 не ждёт ADR 0002.
- **Новые источники `search:` и `archive:`** — новые провайдеры за тем же
  интерфейсом `Provider`; `ResourceRef` расширяется видом источника,
  сохранённые задания этапа 1 читаются без изменений (миграция БД с тестом
  на данных этапа 1).
- **Планы.** Переименование и синхронизация — обычные `OperationPlan` с
  digest, подтверждением и повторной сверкой перед запуском. Удаления в
  синхронизации — отдельный набор шагов плана, который включается только
  явно и требует права delete; по умолчанию пуст.
- **Права агента для новых действий** — существующие: rename/распаковка/
  создание архива/F4 = write, удаления sync = delete, поиск/хеш/сравнение/
  просмотр = read (вместе с содержимым по решению владельца, лимит 1 МиБ на
  ответ, бинарное — только hex-фрагмент).
- **F4** открывает копию через `experimental_openFilePreview` (если окажется
  только просмотром — fallback: открыть копию в редакторе BB через
  file mention/путь; проверяется в S9). Копия — в каталоге данных плагина,
  удаляется после записи или отмены.
- **Лимиты архивов по умолчанию:** 10 ГиБ распакованного, 100 000 записей,
  коэффициент сжатия 1:100 — меняются в настройках; ZIP64 и имена не в
  UTF-8 поддерживаются, если их держит выбранная библиотека.
- **Стенд.** Тот же изолированный BB и Docker; SFTP-проверки пишут ключ
  тестового хоста в реальные known_hosts с последующим удалением (решение
  владельца по этапу 1), пока Remote Hub не починит изоляцию.

## Ограничения

- Архитектура Makosh: `src/core` без хоста, адаптеры в `src/adapters/bb`.
- SDK 0.6.132 / BB 0.50.1; каждое `experimental_*` — в список с fallback.
- Живые проверки SFTP пишут в реальные known_hosts, пока Remote Hub не
  исправит изоляцию helper-а (находка передана).
- Push, теги, установка в рабочий BB — только с «да» владельца.
