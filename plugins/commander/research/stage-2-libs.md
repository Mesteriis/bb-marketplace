# S9 — библиотеки ввода-вывода Commander

Замеры на Mac17,7 (macOS arm64, 64 ГиБ RAM, APFS) с Node 24.20.0 и
оптимизированной сборкой rustc 1.97.0. По одному прогону на операцию.
[Скрипты и команды воспроизведения](s9/README.md).
У каждого ZIP/TAR fixture ровно 100 000 записей: один поток из
2 147 483 648 байт и 99 999 пустых файлов. ZIP записан методом Store,
для JS принудительно включён ZIP64. Набор создавался в каталоге
`mktemp -d`; на чтении проверялись оба счётчика, содержимое сбрасывалось
в пустой приёмник. Пиковая RSS отдельного процесса, без вычитания
базовой памяти, округлена до МиБ. Node сообщает KiB через
`process.resourceUsage().maxRSS`, Rust и Python на macOS — байты через
`getrusage` и `wait4`. Время одного прохода приводится для понимания
стоимости. Кеш ФС, сжатые большие файлы, параллелизм и полные издержки
BB/SFTP отдельно не контролировались.

Для шифрования использовались два малых ZIP64-архива с CP437-именем
`café.txt` и полезной нагрузкой `payload`: AES-256 и ZipCrypto.
Оба прочитаны JS и Rust, неверный пароль отклонён. Защищённая запись
Rust, многогигабайтный deflate, размер/смещение ZIP64 выше 4 ГиБ,
нестандартные кодировки помимо CP437 и перепаковка с сохранением всех
метаданных требуют отдельных проверок. Тест diff проверял ожидаемые строки
и возврат `undefined` при исчерпании бюджета на полностью разных текстах.

Версии и тексты лицензий сверены с реально установленными временными
npm/crate-дистрибутивами, для системной библиотеки — с upstream.
Временная установка npm использовала точные версии и `--ignore-scripts`.
`npm audit` сообщил 0 известных уязвимостей в этой временной выборке.
Полный аудит транзитивных crates и лицензий дистрибутива понадобится при
выборе библиотеки для поставки. Первую пробу TAR на 0.4.44 повторили на
0.4.46 из-за двух бюллетеней по обработке имён, размеров и распаковке.
Тесты читали записи потоком и не вызывали `unpack`. Скрипты измерений и lockfile лежат в [`research/s9/`](s9/README.md).
Логи исходного прогона остались в хранилище треда.

### 7z и RAR

Для `bsdtar` локально получен 7z Store из того же TAR-fixture и выполнено
чтение в stdout без записи файлов на диск, код 0. Отдельно проверены
100 000 записей и 2 147 483 648 байт в stdout. Это замер для Store на
одной сборке, не оценка LZMA2, solid или зашифрованного файла. Поддержку
RAR4/RAR5 у libarchive подтверждает upstream, замер RAR-fixture, solid
и собственное шифрование форматов остаются непроверенными. 7-Zip как
поставочная альтернатива имеет LGPL, BSD-компоненты и ограничение unRAR
для соответствующего кода. Эту альтернативу не собирали и не измеряли.
В S14 реализации 7z/RAR не предлагаются.
[Форматы libarchive 3.7.4](https://github.com/libarchive/libarchive/blob/v3.7.4/doc/libarchive-formats.5) ·
[Лицензии 7-Zip](https://github.com/ip7z/7zip/blob/main/DOC/License.txt)

## Где выполнить работу

JS в сервере BB проще поставить в текущий пакет. Он может читать чанками,
но использует память и цикл событий процесса BB. Запись ZIP с 100 000
записями достигла 1 078 МиБ даже при потоковой подаче. Синхронный diff с
ограниченным входом допустим в JS, а SHA-256 и ограниченный поиск можно
оставить на существующем потоковом вводе-выводе провайдеров.

У Rust-helper отдельная RSS и граница отказа. Для архивов результаты
позволяют принять дополнительные издержки поставки. Пример Remote Hub
использует Cargo.lock, `cargo build --release --locked`, бинарник и SHA-256
в `bin/`, версионированный stdio, supervise и штатное завершение.
Предлагается перенести этот способ поставки на целевые платформы
Commander с ограниченными кадрами и контролем жизненного цикла. Helper
исполняется от имени BB и сам по себе не ограничивает доступ к ФС.
Команду и аргументы задаёт адаптер. Имена и пароли из архива не участвуют
в выборе программы и не попадают в журнал. Все записи проверяются до
создания путей, а данные публикуются только после достижения EOF и
проверки целостности. Подробнее в [ADR 0002](../docs/adr/0002-stage-2-io.md).

## Проба редактора BB 0.50.1

Стенд с собственными HOME, dataDir и портами на loopback, развёрнут по
схеме этапа 1. Минимальный плагин собран с SDK 0.6.132. BB поставлял
в рантайме SDK 0.6.157. Плагин вызвал `experimental_openFilePreview`
из navPanel для синтетической `.txt`-копии, `target.kind="host"`,
`hostId=primaryHostId`, абсолютный путь, `location=null`.

| Состояние | Наблюдение |
| --- | --- |
| Встроенный Monaco выключен по умолчанию | Вызов возвратил `true`, появилась вкладка файла, редактируемой области не было. |
| Monaco включён на стенде | Вызов возвратил `true`, но File Editor показал `This file has no environment to resolve it against`. Редактируемой области не было. Снимок `s9/stand/preview.png` в хранилище треда S9. |

В серверном бандле встроенного Monaco обработчик требует контекст проекта
или среды для цели `host`. Для отсутствующего контекста результат
`true` подтверждает навигацию.

После ревью проверен [свой opener](s9/README.md#редактор-bb-0501) в новом
изолированном BB 0.50.1. Host entry создал синтетический файл через
`experimental_paths.dataDir`. Без параметра `opener` пробный редактор
с `extensions: []` не появился. С явным `opener` открылся и прочитал
`s9-before\n`. Сохранение прошло по цепочке UI → RPC плагина → host RPC.
Отдельный вызов чтения вернул `s9-after\n` с диска. Снимок сохранён в
`s9/stand-repair/s9-editor-saved.png` хранилища треда S9. Fallback через
путь/file mention и реальная запись обратно по SFTP в эту пробу не входили.

## Приёмка S14

Бомбы, traversal и symlink в `zip` и `tar` не проверены. Для S14
поведение проверять на сгенерированных временных fixtures с литеральными
ожиданиями и контролем содержимого папки назначения.

| Fixture | Ожидаемый результат |
| --- | --- |
| TAR с GNU `L` и `K`, PAX `x` и `g`, для каждого заголовок с заявленным телом 256 МиБ | Отказ после 512-байтового заголовка, до чтения тела и вызова `tar::Archive::entries`. Отдельный release-процесс на macOS arm64 с пиком RSS не более 32 МиБ. В тесте счётчик чтения не должен допустить вызов за телом заголовка |
| TAR со служебной записью ровно 1 МиБ и на байт больше. Отдельно цепочка служебных записей суммой больше 4 МиБ, некорректные PAX-длины, конфликт PAX `size`, усечение и переполнение размера/подгонки | На границе 1 МиБ корректная запись читается. Превышение индивидуального/общего лимита даёт отказ до чтения очередного тела. Некорректное или неподдерживаемое представление получает явный отказ. Без публикации файлов |
| ZIP/ZIP64 EOCD с 100 001 записями, каталогом больше 64 МиБ, выходом диапазона за файл, несогласованными дисками, расхождением заявленного и фактического каталога, усечённым ZIP64 locator | Отказ до `ZipArchive::new` и до создания индекса. Корректный ZIP на границе 100 000 записей проходит preflight |
| ZIP с высокой степенью сжатия. ZIP и TAR с превышением суммарного размера, усечённым телом и расхождением ожидаемых и фактических байт | Срабатывает счётчик реально обработанных байт и установленные пределы. Очередь получает отказ, временный результат не публикуется |
| ZIP и TAR с `../x`, `/abs`, `C:\x`, именами с обратной косой чертой, выходящими symlink/hardlink, записью через ссылку, двумя одинаковыми именами и коллизией после нормализации | Никаких записей за пределами цели. Запрещённые пути и типы отклоняются, повторы и коллизии получают явный отказ или разрешаются политикой плана. Тест проверяет исходное содержимое внешнего файла и состояние назначения |
