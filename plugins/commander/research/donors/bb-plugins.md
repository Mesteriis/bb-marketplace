## 2. Файловые операции и безопасность путей

| Операция | XM | FG | WB |
|---|---|---|---|
| list | `src/listing.ts` (cap 5000, `MAX_LIST_ENTRIES`) | host `list` с пагинацией, limit<=200 (`host.ts:29-43`) | host `listDirectory`, 500 записей, кэш 8 с (AGENTS.md, заявлено) |
| read/preview | stream + Range, text<=1 MiB | open/read чанками, UTF-8 текст<=128 KiB за вызов агента | `bb.sdk.files.read` (replace), preview через BB |
| write/upload | да, с докачкой и conflict rename/overwrite/fail | только «copy» в `imports/` с уникальным именем, перезаписи нет | create/replace через `bb.sdk.files.write` |
| mkdir/rename/move/copy/delete | да, все (`src/mutations.ts`); delete = `rm -rf`, не Trash | нет | да; delete в Trash c undo; copy `cp` (verbatimSymlinks) |
| архивы | zip/tar/7z/rar list + extract как job со staging | нет | нет |
| zip-скачивание | потоковый (`src/zip-stream.ts`, 357 строк) | в браузере `fflate`, плоско | нет |

Безопасность путей:
- **XM (сильнее всего).** Жёсткий корень (`homedir`), `realpath` берётся один раз (`root.ts:33`). Три резолвера: `resolveExisting` (realpath ДО проверки префикса, :101-112), `resolveLink` (родитель realpath, финальный симлинк не раскрывается, корень не мутируется, :137-154), `resolveNew` (:160). Строгая проверка префикса с разделителем (:60-64, тест на `${root}-evil`). `validateName` без нормализации Unicode, до 255 байт (:76). Лимиты: `rename` отказывает при существующей цели (`mutations.ts:141`), EXDEV -> cp+rm (:240-264). Минусы: между realpath и операцией остаётся окно TOCTOU (fd/`O_NOFOLLOW` не используются, это вывод из кода, не проверено запуском); при `conflict:"overwrite"` существующая цель удаляется `rm` до записи (`mutations.ts:96-102`, `uploads.ts:641-653`). Тесты: 17 backend-файлов (~330 `it/test` по грепу) плюс 32 frontend и 2 integration; `test/backend/root.test.ts` целиком про escape-атаки (symlink на корень, `/etc`, `${root}-evil`).
- **FG (сильная политика).** Режимы off/folders/all, deny-список, чувствительные компоненты пути по regex (`policy.ts:6`), блок `/proc,/sys,/dev` и `Library/...` (:23). В режиме folders каждый компонент пути проверяется `lstat` на симлинк, потом realpath и повторная lexical-проверка (`policy.ts:27-38`). Открытие файла: `O_NOFOLLOW|O_NONBLOCK`, обычный файл, `nlink===1` вне режима all, проверка размера (`host.ts:44-55`), контроль изменения источника по size+mtime на каждом `read` (:59). Запись: `.partial` с `wx` 0600, имя-базa без `\`/управляющих, `link()` как исключительный коммит без перезаписи (:83-84), сверка SHA-256, TTL сессии 120 с, максимум 8 сессий (:24,27), два одновременных реле-копирования (`server.ts:44,53`). В режиме all симлинки и hard links разрешены намеренно. Тесты: `tests/gateway.test.ts` ~27 тестов на реальных временных файлах (symlink/hardlink, битый checksum, out-of-order, отмена, dispose, офлайн), `tests/remote.test.ts` с реальными ftp-srv и ssh2 серверами.
- **WB (самое слабое для мутаций).** `resolveUnderRoot` чисто лексический, без realpath (`src/paths.ts:13-22`), и комментарий в `host-listing.ts:10` прямо говорит, что симлинки раскрываются, включая выход за корень. Вывод из кода: мутации по пути вида `root/symlinked-dir/x` пойдут через симлинк наружу (`rm`, `rename`, `cp` не сверяют realpath). Защита держится на клиентских opaque `rootId` (`src/roots.ts`, до 500 записей), так что клиент не подставляет произвольные hostId/rootPath. `restoreHostPath` принимает только прямых потомков Trash (:112). Тесты есть (28 `*.test.ts` в `src/` и `lib/`: delete/move/rename/host-trash/search/name-index и т.д.).

## 3. Адресация хостов и удалённых машин (FG)

- Модель: `hostId` = id энролленной BB-машины (`bb.sdk.hosts.list`) либо `remote_<uuid>` для FTP/FTPS/SFTP-«сайта» (`server.ts:50`, префикс `remote_`). Ссылка на файл = `{hostId, path}` строго, `path` абсолютный POSIX (`reference.ts:2`), кодируется `encodeURIComponent(JSON)` в id mention и drag payload.
- Кто выполняет: серверный процесс плагина вызывает host-процесс на нужной машине через `bb.hosts.experimental_client` (`host.call(op,input,{hostId,signal})`); хостовый код из `host.ts` разворачивается BB лениво (README FG). Удалённые FTP/SFTP работают только из серверного процесса плагина.
- Политика хранится на стороне сервера плагина (`cfg.shares[hostId]`) и передаётся в host-вызов на каждый вызов (`policy` в input), хост ей доверяет; для режима all хост не добавляет ограничений.
- Ограничения передачи: BB-хост -> BB-хост до 256 MiB (настраиваемый `maxFileMiB` 1..256), сайты -> BB-хост до 32 MiB и только вниз (`connections.ts:19`), файл с сайта сначала целиком собирается в памяти (`downloadBounded`, `remote.ts:42-49`, `Buffer.concat`), и только потом чанкуется. Записи на удалённые сайты нет (нет upload/edit). Назначение только `imports/` внутри `dataDir` плагина на машине-получателе, не произвольная папка. Папки не копируются, возобновления нет.
- SFTP: только пароль, обязательный SHA-256 отпечаток хост-ключа (`connections-contract.ts:3` refine + `remote.ts:24` `hostVerifier`), симлинк на выход из connection root блокируется через `realPath` (`remote.ts:27`); FTP: симлинки запрещены (`remote.ts:29`), глубина <=64. Максимум 30 подключений (`connections.ts:7`). Каждая операция открывает новое соединение, таймаут 60 с (`remote.ts:20`). Ошибки обезличены («Remote operation failed...»), что скрывает причину от отладки.
- `ssh2-sftp-client` подгружается через `createRequire` в обход бандлера (`remote.ts:4-5`), значит, плагин требует сохранённых `node_modules` на установке (заявлено в README FG).

## 4. Workbench Explorer: тред, редактор, жизненный цикл, поиск

- Связь с тредом: `workspaceForThread` (thread -> environment -> hostId/path); у Commander нет собственной модели, поэтому именно этот путь (`bb.sdk.threads.get` + `bb.sdk.environments.get`) нужен для «панели у треда». Тот же вызов в FG (`server.ts:113,119`) и XM (`src/locate.ts:84,226`).
- Редактор: штатного редактора в SDK нет, есть только `experimental_openFilePreview` (target workspace или host, `location` для строки/колонки) и `experimental_openFileExternally`; `fileOpener` (XM) подменяет просмотрщик по расширению, исключительный слот на расширение.
- Жизненный цикл UI: `experimental_appOverlay` монтируется один раз на окно BB, навигация его не размонтирует; состояние держится в localStorage и custom-event шинах (`rail-state.ts`, `reveal-bus.ts`, `chat-draft-bus.ts`). У `navPanel` (XM) состояние теряется при закрытии страницы: XM нарочно не использует `fixedTabs`, потому что смонтирован только активный fixed tab (`app.tsx:3-8`, комментарий). Внутри panel-tab папка хранится в state, а не в маршруте (`FileManagerTab.tsx:8-12`).
- Поиск: см. выше (ripgrep WASM на хосте + JS-матчер, пределы 4000/24/1 MB; Quick Open fuzzy; name-index). В XM поиск проще: `searchDir` depth<=8, <=500 результатов (`contract.ts:97-98`).

## 6. Выводы

1. Лучший донор для файловой механики Commander: **XM**. Модель резолверов путей (`root.ts`), полный набор мутаций с политикой конфликтов, HTTP-стрим скачивания с Range/ETag, потоковый zip, upload с докачкой, realtime-сигналы, `navPanel` + `experimental_tab`. Ограничения: единственный корень `homedir`, только primary-хост (`rpc.ts:60`), нет host-процесса, нет удалённых файловых систем.
2. Лучший донор для мульти-хоста и безопасной адресации: **FG**: `{hostId,path}`, `Policy`, `O_NOFOLLOW`+`nlink`, exclusive-`link()` коммит, SHA-256, лимиты сессий, тесты на реальных файловых серверах. Минусы: base64 в RPC, пароль-only SFTP, чтение сайта целиком в память, нет записи на удалённые сайты, нет `navPanel`.
3. **WB** даёт идеи UX: постоянная панель (`appOverlay`), команды с горячими клавишами, Quick Open, ripgrep на хосте, Trash+undo, `bb.sdk.files.*` на любом хосте. Для мутаций его confinement лексический (symlink-обход вероятен) - брать только UI-идеи, а не `paths.ts`.
4. Объём и протокол передачи: ни один донор не даёт эффективной передачи крупных файлов между хостами/по SFTP. HTTP-стрим (XM) работает только для файлов на машине BB-сервера (с `auth:"local"`/`token`), а RPC-реле (FG) упирается в base64 + 256 MiB. Для SFTP и больших файлов нужен собственный хелпер (вероятно Rust) со стримингом и докачкой. Это предположение для проектирования, в донорах не проверялось.
5. Версионная совместимость: тянуть минимум SDK 0.6.x (XM 0.6.132, get-bb 0.6.205); `navPanel` и `fileOpener` есть в 0.6.x, FG на 0.4.87 их не использует. Много слотов помечены `experimental_*` (tab, newThreadPanelAction, threadHeaderAction, appOverlay, openFilePreview, saveFile, defineHostEntry, hosts.experimental_client): API нестабилен, закладывать адаптер и проверку `bb plugin types --check` (XM `package.json` скрипт `types:check`).
6. Правила репозитория: `src/core` и `src/ui` без `@get-bb/*`, `node:*`; value-импорт SDK из contract-файла, который тянет frontend, ломает установку (урок XM `contract.ts:9-16`). Любой переносимый код записывать в `THIRD_PARTY_NOTICES.md` (все три донора MIT, нужен copyright-текст каждого).
7. Что НЕ брать: WB `paths.ts`/`host-trash.ts` без realpath-усиления; FG `remote.ts` как есть (память, пароль-only); XM `overwrite` через `rm`; вложенный DOM-хак drop-target FG.
8. Риски безопасности для Commander: (а) TOCTOU между realpath и операцией (XM, WB), (б) режим «Full computer» FG разрешает всё, что читает BB, включая секреты и симлинки, (в) содержимое сообщений и файлов - данные, не инструкции (в XM resolve вкладывает до 256 KiB файла в контекст агента, нужна явная метка/fence, XM делает fence длиннее backtick-run), (г) единый JSON-блоб паролей FG в одной секретной настройке.
