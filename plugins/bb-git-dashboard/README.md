# Makosh Git

Plugin ID and package name are both `bb-git-dashboard`; the display name is **Makosh Git**. The navigation entry is **Git**. Makosh Credential Vault is an optional integration.

The Git sidebar groups projects by the parent directory of their default BB source. Search by project or folder name above the independently scrolling list. Projects without a source appear under «Без папки».

The sidebar is the panel's one navigation: **Overview**, **My PRs**, **CI/CD**, **Reviews**, **Projects** and **Catalog** with their counts, the projects folder tree, **Connections** (the connected accounts, a new connection and the accounts' repositories) and the interface language. Press `/` to search.

The plugin's own section on its BB settings page sets the main settings in the interface language and in groups: the projects folder; the language and how the overview opens; the alerts on failing CI and on comments, with a test notification; whether AI runs are approved for you; the folder of own CI templates. Each change is written at once, only these settings (`settingsSet` refuses any other key), each by the part of the plugin that owns it. BB's flat list of every setting stays above it.

**Overview** opens the panel: a list of what needs your action, what you can finish and what goes on without you, with the chosen item's details and the way to its action, or a board by stage (local, PR open, in review, ready, merged this week) with the runs going on now. It reads through the plugin's existing calls — My PRs (open and review requested; merged for the board), CI/CD and the status of up to 50 attached copies — keeps a complete read for five minutes and writes nothing; Refresh reads again. Ready to merge means green CI and an approval as the forge reports them; a forge that reports neither (Gitea's review decision, Azure's CI) never shows a pull request as ready. **Overview opens as** chooses list or board.

Both views show the same objects. Everything in the list is on the board: my pull requests in the stage they are in (open, in review, ready), reviews asked of me in **In review** marked as waiting for me, unpushed or never-published copies and copies behind origin in **Local** (one card per copy, with both distances), and what runs in **CI now** (the copies' runs and my pull requests' CI), which also shows the last run of a repository that failed within a day. The board adds only what needs nothing from me yet: my drafts and pull requests waiting on others, and those merged this week. A card's button is the list row's action; a click on the card takes it too, and Tab reaches the button. The language follows BB's (Russian for a Russian BB, English otherwise) until RU or EN is chosen in the sidebar or **Interface language** in the plugin settings; sections take the setting as they move to the new interface, the sidebar first.

## Build and install

From this directory, with Node 22.18+ and BB 0.50.1+:

```sh
npm ci
npm run check
npm run build
```

For a prebuilt `bb-git-dashboard-0.2.0.tgz`, unpack it into a new directory, enter `package/` and run `npm install --omit=dev --ignore-scripts`. A BB path install still resolves the host entry's Zod dependency from the package directory.

Run `bb plugin install "$PWD" --yes` from a **test profile** to install the prepared directory. Check for `bb-git-dashboard` in `bb plugin list --json`, then open **Git** in BB Web. The acceptance artifacts include an isolated profile launcher and browser scenario for BB 0.50.1. Installing or removing a plugin in an owner's BB profile requires their go-ahead.

## Project workspace

**Projects** is one table of the attached copies, grouped by category — the folder below the projects folder a project sits in (Personal, Work); projects straight in the projects folder take its name. Each row shows the forge and repository under the name (the machine and path when another copy of the repository is listed), the branch, the number of changed files, ↑↓ against upstream (or that the branch was never published), my open pull request of that branch with its state, and the last CI run of the copy's branch, with the copy's machine and path under its name. The views count and filter the rows: **All**, **Need attention** (CI failed, a conflict or requested changes in my pull request, behind origin), **With changes** (changed files or commits not pushed), **My PRs**, **CI failed**. Search matches project, branch, upstream and repository. Chosen rows are fetched or pulled together (at most 50, those in the projects folder; others answer with the reason; a pull that could not fast-forward says so). Copies of no project are `project/` (Not in a project). A source that was not read is named above the table. The table reads what the overview reads and keeps it for the same five minutes; it has no commit column, since a copy's status carries no commit message or time. `project/<id>` is the same table for one project. **Attach a copy** chooses a project source or environment, or a path on a machine; the attached copy opens. The overview's head filters by category: copies of that category, and pull requests of their repositories; a pull request with no attached copy shows only under **All**.

A copy's page has its branch and ↑↓ in the head with **Fetch**, **Pull** (fast-forward to upstream) and **Push**, which says in a dialog what it pushes where before it does (to a local bare origin). A network origin is fetched from and pushed to through the account the copy is linked to (on its CI/CD tab), after the server's preview of what it will do; **Create pull request** in the head opens one from the branch the same way — base, title, description, then the preview. The sections are tabs: **Code**, **History**, **Review**, **CI/CD**, **Issues**, **Variables**. **Code** has **Changes** (staged and not staged files with check boxes, **Stage all** and **Unstage all**, the flat diff with each hunk's action under it and **Open in review**, outgoing commits, and at the bottom the message, the author as one line — click it to change it for this commit — **Commit** and **Commit and push**), **Branches** (search, local or remote, comparison of two branches, a table of what each tracks, how far it is and its last commit from one `for-each-ref`, with Switch, Merge into current and Rebase onto… under ⋯, and **Create branch** in a dialog), **Worktrees** (a table of the repository's worktrees with Open, and **Create worktree** in a dialog) and **Activity** (each operation in words with its result, who and when), with the copy's machine and its path from `~`. Worktrees that share one Git administration directory on the same host appear under one repository. **Ask an agent** on an issue opens BB's composer with the issue's title and text fenced as data.

**Attach a copy** also takes an absolute trusted path on the selected host. Previously attached copies are matched to BB projects by exact host and path; a copy without a project's folder is under **No folder**. Linked worktrees open from **Code → Worktrees**. To clone from a local bare repository, supply the bare source and a new destination whose parent already exists.

**Actions**, **Issues** and **Variables** read data for the selected repository. The panel detects the forge and account from the working copy’s `origin` and connects the repository on its own; when the choice is ambiguous it asks for the account. A provider account and repository can still be chosen by hand from the connection form. The plugin verifies that the provider repository is the working copy’s `origin`, comparing SSH and HTTPS forms of the same repository. HTTPS fetch and push still require the HTTPS `origin` itself. GitHub and supported Gitea instances expose CI/CD runs, issues, repository variables and secret names. GitLab exposes pipelines, issues and CI/CD variables by name, type, protection, masking and environment, never their values; reading variables needs the Maintainer role. Azure Repos exposes builds filtered by the Git repository. Azure Boards and variable groups are project-scoped. The views display up to 30 entries per list. Secret values are never returned. Run and issue links open the provider’s own views when the provider supplies a link on its configured origin.

**Git beside a thread** is one tab, fixed, for the working copy of the thread's environment. Its head has the copy's name and forge, Pull and Push (Push asks first, in the same dialog as the copy's page), and the branch, where it goes (the pull request's base, else its upstream) and how far apart. Under it a summary in parts that fold (the panel keeps them as left for the browser tab's life): **Changes** — each file with a box that puts it in the index or takes it out, a commit message and Commit N of what is staged; **Pull request** — the open one from this branch (from My PRs' Open tab, read once a minute at most) with its state as chips and Open; **CI** — the branch's last run with its jobs as chips and, when it failed, the error line and the next one, Fix with agent, Re-run (asked first) and Log; **Review** — the open comments of the copy's reviews and Open the review; **History** — the commits not pushed and when the last one was made. Each part opens its full screen in the panel with a way back: the copy's Code (Changes, Branches, Worktrees, Activity), the run, the review, the history. The thread header's Review and Git History buttons, the Review commands of the palette and the Review row of the thread's Info open the Git tab on that screen. The agent's access to the copy is chosen under the summary. A copy pinned from its page (Pin) and a pull request pinned from its page (⋯ → Pin as a tab; pinning it again selects its tab) stand in the Git page's side panel: the same panel with "Pinned copy · not this thread's working copy", and the pull request's page under "Pinned pull request · repository · forge", each with Unpin, which says so when the tab is no longer open. A file chosen in the summary opens Code with that file shown. The thread header's buttons are labelled in the interface language. The panel takes the width BB gives it (about 560 px) and fits from 420 to 640 px.

**History** draws the commit graph of a working copy, also as a screen of the thread's **Git** tab (the thread header button set by `historyHeaderShortcut` opens it there). `historyGraph` off lists commits without lanes. Its bar has Find in loaded commits (only what is loaded; Show more extends it), **All branches** or **Current only** (the loaded commits reachable from HEAD), the count and the branch, and Refresh; the chosen commit shows its hash to copy, author, parents and changes, its files with their counts and the chosen file's diff with line numbers and Wrap lines. A patch is read up to 1.5 MB and cut at a whole line beyond that.

**CI/CD** in the sidebar sums up the latest runs of every linked repository, one copy per repository: a line of numbers (running, queued, failed, how often the finished runs shown succeeded) and a table of run, repository, state, branch, event, start and duration; a row opens that run. A run is a page addressed as `<copy>/actions/<run>`, with its path back, Re-run failed jobs, Re-run all or Cancel, Ask agent (at once, or with the model chosen in the composer), Send to threads, Run with inputs, the jobs with their durations and the log at its error line with a filter, Follow the end and Copy log. **Run workflow** is a dialog that shows what the server will send — its own preview, asked once the form rests — and sends exactly that preview on Run. **Templates** are `<copy>/actions/templates`: the list, the values and the file side by side. A thread's **CI/CD** tab shows the thread's working copy and adds **Send to this thread**. `ciFallbackProject` is the project whose threads investigate and receive runs of copies outside any BB project; such a thread starts in the project's default environment, not in the copy. `ciAnalysisModel` sets the model of new investigation threads. Send to threads remembers its last five recipients per copy in the browser.

`bb git-dashboard ci list|show|workflows|run|rerun|cancel` works from a BB thread on that thread's working copy: reads need the Read grant, and writes need Stage and commit plus the owner's approval of the previewed write in the thread. Workflow inputs are checked against the workflow's declared ones before anyone is asked.

## Line review

**Reviews** in the sidebar is one table of the line reviews that have comments: the working copy, what it looks at, open of all comments, where the agent stands (answers waiting for you, or when the comments were sent) and the last AI review (running, done with how many findings — the threads an agent opened while it ran — failed, or not run); a row opens that review. Reviews of copies that are gone are listed below with Delete, which asks first.

A copy's **Review** has one bar: the view, the number of files and lines, **Unified** or **Side by side**, **View ▾** (Hide whitespace, Only files with comments, Wrap lines, previous and next comment, Go to, Comment on the diff, Reload, Clear review), Find, **AI review** (a dialog: review or summary, focuses, what else to look at, the model) and **Send to agent N**. The files are listed on the left with a box to mark each Viewed and their open comments; threads no longer on the diff are listed under them. A new comment's severity is chosen in its head.

**Review** reads a working copy's diff on its own host: `uncommitted` (HEAD against the working tree, untracked files included), `staged`, `unstaged`, `branch` (commits since the base's merge base), `all` (the merge base against the working tree), `commit` (against its first parent) or a `range` (`a..b` from their merge base, `a...b` from where a merged branch forked). The base defaults to `origin/HEAD`, then `main`, then `master`. Comments are kept in the plugin's SQLite database, one review per copy and view. Send to agent writes one message into a thread whose environment is the copy; the agent may answer only the comment threads whose last send went to its own thread (`bb git-dashboard review …` with the calling thread, or the `git_review_*` tools), and a thread it leaves unanswered at the end of a turn that began after the send shows "No reply". Apply suggestion reads the file (a regular text file up to 1 MB inside the copy, no links) and writes it back through a temporary file only if its SHA-256 is still the one read.

## My PRs

**My PRs** opens the pull requests of every connected account, by tab (Open, Review requested, Reviewed, Assigned, Merged, Closed) and grouped by repository with its forge. Each row says its state in words (CI failed, Conflict, Changes requested, N unanswered, Draft, On #N, CI running, Ready to merge) next to a coloured edge; the chips above the list count CI failed, Conflict, Changes requested, Unanswered and Ready to merge and filter the rows by one of them. New alerts since you last looked stand in one line with Mark as seen. `j`/`k` move through the rows, `/` searches. GitHub uses GraphQL search; GitLab the global merge request list by scope (Reviewed lists merge requests you review and approved: GitLab has no reviewed-by filter); Gitea `/repos/issues/search` plus each open pull request's details and head status; Azure the pull requests of each project of the organization (the first 30). A tab shows a total only when every account that answered can count it. Alerts come from a background check, configured in the plugin settings `inboxNotifyCi`, `inboxNotifyComments`, `inboxToasts`, `inboxDesktop`, `inboxBadge`, `inboxIgnore` and `inboxEveryMinutes` (2–60, default 5); the check keeps one baseline per account in plugin storage and stores the last 50 alerts. Push notifications are sent through the `push-notifications` plugin when it is installed.

## Pull requests and issues

A pull request page has its path (My PRs › repository), its place in the list it was opened from with `[` and `]`, the title with its state, Open on the forge and ⋯, and the branches it merges. Its tabs: **Overview** (the description, the discussion with a comment box, and beside them what keeps it from merging — CI with how many checks passed, the review with approvals and comments without an answer, conflicts with the base — each leading to its tab, the reviewers, the merge with what the forge may still hold it for, Fix all with agent, Convert to draft and Close), **Checks** (a table; a failed check opened on its errors with the whole log and Fix with agent), **Files** (the files beside their diffs, unified or split, wrapped or not), **Commits** (hash with copy, message, author, when, CI) and **Comments** (open, resolved or all threads as rows with Reply, Resolve, Fix with agent and To line; an agent's draft answer stands in the reply's place with Send, Edit and Discard; beside them your review — its outcome, a summary and the line comments it takes — and the participants' reviews). A pull request page is addressed as `pr/<account>/<number>/<repository path>` in the Git panel and opens from My PRs. It reads GitHub through GraphQL (detail) and REST (files), GitLab through the merge request, its discussions, approvals, diffs and commits, Gitea through the pull request, its issue comments, reviews and review comments, statuses, files and `.diff`, and Azure DevOps through the pull request, its threads, statuses, commits and latest iteration's changes. Writes go through a preview that is confirmed once within five minutes and refused when the head moved: GitHub line comments and reviews are pinned to the head commit; GitLab line comments are diff discussions anchored with the merge request's diff refs, approvals carry the head sha and the draft state is the title's `Draft:` prefix; Gitea line comments and reviews use the reviews API with the head commit and the draft state is the title's `WIP:` prefix; Azure approve and reject are reviewer votes and a merge is a completion that Azure finishes later. Fix with agent finds projects whose git remote is the repository and sends the prompt to the newest open thread on the pull request's branch, else starts a thread in the first such project's default environment. Issues are read and written for GitHub, GitLab and Gitea; Azure Boards are outside the repository. Only the pull request or issue itself must be readable: a failed part (discussions, reviews, commits, statuses, your own user) is named on the page. A read refused by a rate limit that names its reset within two minutes is tried again by the page after that many seconds.

## Accounts and transport

**Git → Connections** lists the connected accounts. **Check** signs in with an account's stored token and says what it found: the login, how many repositories it opens, a classic GitHub token's scopes and end, a GitLab token's scopes and end, a Gitea server's version — and from that **Works**, **Works with a limit** (no `workflow` on GitHub, no `api` on GitLab), **Expires soon** (within 7 days), **Token expired**, **Another login** or **Does not work**; the last check is kept per account until its declaration changes or its token changes in the plugin's settings. Plugin storage keeps only the check's result (login, repository count, scopes, end, version or failure code, when) beside the account's declaration — never the token or anything computed from it; a token rotated in Vault outside the plugin leaves the old check showing its time. Below, the servers of the projects folder's remotes are counted with the account on each; a server with none has **Connect**. **Publication activity** at the bottom shows, when asked, the clones, fetches, pushes and pull requests done through the accounts with their result. **Connect account** opens the wizard in three steps. **Server type**: enter any repository's address — public GitHub, GitLab and Azure DevOps are recognized, with the Azure organization — or choose the type (GitHub, GitHub Enterprise, GitLab, GitLab self-managed, Gitea, Azure DevOps). **Access**: the token, sent only to the shown address. **Check**: the login and the repositories it opens, and an optional name. The Azure wizard asks for the Git username used by the transport. The token is persisted only after you select **Connect**. With Makosh Credential Vault enabled, Git Dashboard writes to Vault and keeps a fallback copy in its built-in secret settings.

For manual configuration, the plugin’s BB settings accept two JSON values. Account declarations are ordinary metadata. API tokens belong in **Provider API tokens by account ID**, a BB secret setting.

```json
[
  {"id":"gh-a","kind":"github","label":"GitHub A","origin":"https://api.github.com","username":"alice"},
  {"id":"azure-test","kind":"azure","label":"Azure Test","origin":"https://dev.azure.com","organization":"example-org","username":"tester"},
  {"id":"gitea-test","kind":"gitea","label":"Gitea Test","origin":"https://git.example.invalid","username":"tester"},
  {"id":"gitlab-test","kind":"gitlab","label":"GitLab Test","origin":"https://gitlab.example.invalid:8443","username":"tester"}
]
```

The token value is a JSON object keyed by these IDs. When Vault is enabled, the dashboard migrates pre-existing tokens on load or on first use of an account. It inserts only when the Vault reference is absent and verifies the encrypted record by reading it back. The record is bound to the account ID, provider, API origin, organization and username. When Vault is missing or disabled, the dashboard uses the copy in BB’s secret settings. An enabled but locked or failing Vault reports an error. If a previously verified record disappears, the dashboard does not recreate it from the fallback copy. Use a distinct ID for each account and grant only the provider permissions it needs. Use the canonical HTTPS instance origin. Azure targets Azure DevOps Services and takes the organization separately. Gitea targets the v1 API at the origin root, GitLab the v4 API at the origin root. A GitLab token needs the `read_api` scope to read and `api` for merge request and pipeline actions. Repository, account and origin selected for an operation are displayed before confirmation.

Git transport credentials are separate from API tokens. Provision the account's Git credential on the selected execution host using the macOS Git OS Keychain helper. The helper entry must be scoped by HTTPS protocol, host, exact repository path and username. HTTPS Git transport currently supports macOS hosts with this helper. Configure the account using the username that uniquely identifies the corresponding keychain record. A repository created from **New project** is pushed the same way (on macOS; on another machine the preview says so, and the repository is made empty — set origin, add the credential, push main and link it by hand): once the forge has made it with the account, the plugin saves the account's token in the Keychain for that repository's exact address and the account's username (`git credential approve` with the host's own `git`, the token on stdin only, so the push finds it and macOS does not ask for access), then pushes main. The preview says so before confirming, and the activity log records the entry without its value. The entry is read back through the same `git` and helper; if the Keychain did not keep it, main is not pushed, the repository stays empty with origin set, and the answer says why; nothing is saved for a repository whose creation was not confirmed. A self-hosted forge on a private certificate authority: set `MAKOSH_GIT_CA_FILE` for BB to its CA bundle, which HTTPS Git then verifies against instead of the system one. Commit author configuration is separate from both credentials. Existing local `user.name` and `user.email` are used when present. The dashboard can supply an author for a single commit.

To disable an account, remove its declaration and secret map entry in BB and delete the matching repository-scoped Git credential from that host. Configuration changes invalidate pending publication previews. Refresh the catalog after changing the account's access. Previous operations retain non-secret audit metadata.

## Boundaries

- Choose repositories whose local Git configuration you control. Attach verifies a canonical root and ties the registration to the filesystem identities of the worktree and Git administration directories. Git rejects nonstandard config keys, uses an isolated environment, and disables hooks, external filters, alternate network schemes, redirects, and submodule recursion. Same-user processes with shell access can still modify Git or the filesystem independently.
- Local index edits use Git's index lock. Commits use a copied index and compare-and-swap the expected ref. Merge, rebase and cherry-pick sequences are finished outside the dashboard. The plugin does not expose reset, clean, force push or policy bypass. Git status and patch output have bounded UTF-8 buffers.
- Agent access defaults to revoked and is tied to a specific thread and registered copy. Publication and new agent work each require a separate confirmation in BB. Changes sent through the app or an agent tool use the same backend. A closed tab, disabled plugin, or unmanaged environment removal leaves checked-out files in place.
- Azure can return an asynchronous completion. The activity view distinguishes that from a completed merge. Azure supplies changed paths in its REST PR API. For a textual comparison, select a working copy with both commit objects. The initial Azure adapter accepts mutations of same-repository PRs. GitHub and Gitea return provider diff and check details as available under the selected credentials.
- Unknown outcomes are recorded without a retry. Inspect the remote branch or PR before choosing a new action. Publication confirmations are short-lived and expire on server reload. The durable journal contains the outcome, actor and non-secret destination and revisions.
- BB's native tab API supplies context and pinned tabs. A Chertog tile integration is outside this package. The provider credential flows, agent session, parallel live identity test and review-agent isolation need a live test environment for acceptance.

Catalog discovery accepts BB branch ownership metadata, GitHub CLI remote metadata, credential helper declarations and per-worktree configuration. It checks configuration keys in both repository and worktree scopes. Only identity lookup and worktree enumeration use this policy. File status, changes and transport still require the stricter operation policy.

The sidebar folds single-child directory chains and lets you expand nested folders. Open the project’s ⋯ button to inspect each BB source and its host, hide the project from Git Workspace, unlink a source in BB, or move its local Git folder to the macOS Trash. Hidden projects can be restored at the bottom of the list. Moving a folder requires its full path and leaves the BB source registration available to unlink. Repositories with linked worktrees must be handled separately.
