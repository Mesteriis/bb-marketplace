# Живой экран провайдера в тайле Чертога

**Решение для одного окна — overlay владельца с React-порталом в постоянный DOM-контейнер Чертога.** BB монтирует корень Telegram, Zoom или Remote Hub через его собственную регистрацию `experimental_appOverlay`. Владелец создаёт содержимое портала и вызывает свои SDK-хуки. Чертог предоставляет пустой контейнер, располагает его и получает только состояние вида и непрозрачную ссылку. Между пакетами нужен небольшой версионированный протокол окна. SDK даёт слот для корня, а протокол предстоит реализовать в адаптерах четырёх плагинов.

Это проект решения на базе `chertog@33c96465` для доверенных установленных плагинов BB 0.50.1. Общий документ позволяет его скриптам читать DOM. Гарантия здесь — отсутствие передачи приватных данных через контракт, хранилище и журналы Чертога. Для изоляции от враждебного плагина, способного читать документ или рисовать поверх него, нужен отдельный защищённый контекст хоста. В текущей версии работают карточки. Пути ниже отсчитываются от корня репозитория, внутри раздела провайдера — от его каталога.

## Почему выбран портал

| Вариант | Доказательство и следствие |
|---|---|
| HTTP-страница со своим бандлом в iframe | Образец `plugins/chertog/src/adapters/bb/server/live-frame-route.ts:41` читает фиксированный файл из пакета, строка 55 регистрирует GET. Для приложения потребуются собственные сборка HTML/JS/CSS, разрешённые фиксированные маршруты и политика CSP. В SDK 0.6.157, `bundled-types/bb-plugin-sdk.d.ts:20780` и `:20802`, у HTTP и WebSocket три режима. По умолчанию local проверяет Origin/Host и тип тела для записи. Контракт не удостоверяет пользователя или вызывающий pluginId по сессии BB. Token требует секрета маршрута, none снимает проверку. Доставка cookie браузером сама по себе ничего здесь не доказывает. SDK-функции фронтенда берутся из runtime текущего globalThis (`@get-bb/plugin-sdk/dist/app.js:214`, `:228`, `:320`). Свежий документ iframe такого runtime и host-контекста не получает. Собственная копия React этого не меняет. Прямой fetch вместо owner RPC или мост, передающий Чертогу клиент, открыл бы новый путь к данным. Iframe подходит для уже самостоятельной внутренней страницы, например страницы звонка Zoom, но не для переноса всего штатного экрана с его полномочиями. |
| Реестр компонентов по ключу версии, рендер в дереве Чертога | В установленной сборке `bb-app/app/dist/assets/plugin-frontend-DoZPU-CF.js:8` загрузчик фронтендов инициализирует один runtime окна (`DL`, поля react, reactDom и pluginSdkApp). Общий документ и React делают совместный рендер технически возможным. В том же файле на строке 6 функции `eh` и `th` берут текущий ID через один accessor `Vr()`: RPC адресуется этому ID, realtime фильтрует сигналы по нему. На строке 8 это реализации useRpc и useRealtime. Компонент, вызванный под корнем Чертога, наследует scope Чертога. Имя модуля, ключ реестра и параметр pluginId не устанавливают scope. Передача привязанного RPC-клиента или копирование внутреннего контекста в Чертог делегировали бы чужие полномочия. |
| Собственный публичный слот владельца | `bundled-types/bb-plugin-sdk-app.d.ts:19537`, `:20292`, `:22988` задают overlay-компонент с SDK-хуками. Жизненный цикл окна уже использует `plugins/terminals/app.tsx:34`. React-портал сохраняет контекст дерева, вызвавшего createPortal. Примеры порталов в этом репозитории — `plugins/telegram/src/ui/telegram-page.tsx:436`, `plugins/telegram/src/ui/chat-details.tsx:214`. Закреплённый контейнер уже реализует `plugins/chertog/src/ui/live-hosts/LiveHostLayer.tsx:111`, `:151`: ключ instanceId, перемещение и скрытие стилями. Чужие navPanel и вкладку напрямую получить нельзя: SDK регистрирует navPanel у владельца (`bb-plugin-sdk-app.d.ts:22995`), ThreadChat принимает threadId (`:23752`), cross-plugin callRpc передаёт данные с идентичностью вызывающего (`:18470`, `bb-plugin-sdk.d.ts:20835`), ни одна из этих операций не монтирует внешний экран. |

Идентификаторы минифицированной сборки приведены для воспроизводимой проверки этой версии. Адаптеры используют обычный React и публичные импорты SDK. Доступ к внутренним runtime-глобалам для реализации не нужен. См. [пин SDK](sdk-version.md), [проверку поверхностей](discovery-providers.md) и [границы HTTP и RPC](stage-b-integration.md#почему-чужие-http-и-rpc-не-дают-живой-экран).

## Контракт одного окна

1. Чертог по действию «Добавить» предлагает тип. Внутри слота владельца пользователь выбирает разрешённый ресурс. Провайдер создаёт или находит стабильный случайный UUID v4 для пары «владелец/ресурс», сверяет доступ при каждом разрешении. Запись связи хранит сам провайдер. UUID представляет ссылку, владение им не даёт права читать, писать, подключаться или входить. Восстановление может показать «требуется выбор», «нет доступа» или «сессия завершена». При смене аккаунта доступ пересчитывается до первого чтения или действия.
2. Ввести протокол документа `chertog.embed.v1` между доверенными адаптерами. Чертог объявляет контейнер с типом, instanceId, поколением попытки и ссылкой либо режимом выбора. Overlay подписывается при mount, запрашивает текущие контейнеры и сообщает готовность. Повторное объявление для того же узла и поколения идемпотентно. В обе стороны проверяются версия, тип, актуальный узел в слое этого окна, поколение и допустимое состояние. Для выбора ответ привязан к открывшему его экземпляру. События DOM не удостоверяют пользователя или автора события. Любое изменение привязки, передача ввода, подключение, вход и выход требуют проверки и явного действия в интерфейсе владельца. Через события не проходят произвольные команды, RPC-клиенты, renderer-функции, билеты, URL, заголовки, текст или вложения.
3. Для каждого активного запроса owner overlay вызывает createPortal с одним контейнером и неизменным ключом экземпляра. Условие готовности сейчас в `plugins/chertog/src/adapters/bb/app/PanelContent.tsx:14` допускает render только после live/entry. Для embed контейнер нужен **уже при выборе и загрузке**, в том же месте и с тем же ключом после ready. Иначе open ждёт узел, который появится только после open. Спиннер/ошибка — соседнее содержимое. Через `content-sources.ts:29` и `src/core/panels/provider.ts` Чертог переводит вид в live только по подтверждению владельца. Поздние ответы прежнего поколения игнорируются. Тайм-аут при неопределённом исходе даёт unknown.
4. Геометрию и скрытие выполняет существующий LiveLayer (`plugins/chertog/src/adapters/bb/app/LiveLayer.tsx:34`). Вкладка, split, maximize, drag и уход с маршрута сохраняют узел, portal target и его родителя. Скрытый вид теряет ввод и видимость для агента. Отзыв, reload или disable провайдера размонтирует owner overlay и его порталы, освобождает listeners/attach, отзывает регистрацию поколения; Чертог показывает недоступность. При аварии без cleanup нужен контроль доступности экземпляра владельца с ограниченным временем ожидания. Потеря связи означает lost/unknown. Новая регистрация не повторяет вход, отправку, подключение или доверие сертификату.
5. Запрос убрать тайл проходит через текущий реестр (`plugins/chertog/src/core/panels/registry.ts:267`). Скрытие сохраняет привязку. Для последнего разрушающего вида владелец предлагает оставить скрытым, отменить или завершить. До ответа остаются узел и сессия; после подтверждения владелец завершает один раз и подтверждает результат, только затем источник освобождается. Неполученный ответ оставляет предупреждение. Отзыв хостом может уничтожить вид принудительно. Для всех типов межоконная передача остаётся выключенной.

### Первый выбор до появления ссылки

Сейчас `plugins/chertog/src/adapters/bb/app/workspace-session.ts:278` требует результат refOf до изменения раскладки. Для команды «Добавить вид» нужен отдельный вход в WorkspaceSession, который вызывается **до** этого пути. Предлагается следующий жизненный цикл.

1. WorkspaceSession проверяет наличие владельца, место в группе и лимит панелей. Она резервирует новый panelId, а PanelRegistry резервирует instanceId из своего генератора с возможностью однократного принятия или отмены. Резерв хранится только в памяти окна. В нём есть тип, поколение, исходный layoutId и назначение. PanelRef и записи панели в сохраняемом документе пока нет. Занятое место учитывается при следующих добавлениях.
2. LiveLayer сейчас перечисляет только записи registry.list() (`src/adapters/bb/app/LiveLayer.tsx:35`). Для выбора он должен включать и резервы из WorkspaceSession в **тот же** список LiveHostLayer, по одному элементу на instanceId. Визуальная раскладка показывает временный тайл в назначении и даёт ему прямоугольник. И панель выбора, и будущий экран используют один постоянный контейнер внутри LiveHost с тем же React key. Контейнер существует до появления viewOf, независимо от ветки состояния PanelContent. Owner overlay рисует туда выбор ресурса. До подтверждения допускается просмотр каталога; attach, join и отправка отсутствуют.
3. При ответе владельца WorkspaceSession сверяет поколение, доступность назначения, лимит и обе схемы ссылки. В одной операции модели она регистрирует валидный PanelRef под зарезервированным panelId, размещает его и связывает panelId с принятым instanceId. Реестр использует **зарезервированный** ID вместо повторного вызова ids.nextId. Согласование реестра с раскладкой и уведомление React происходят после установки обеих связей. Между резервом и обычной записью нет кадра с удалённым ключом. Overlay переключает содержимое существующего портала на экран ресурса. Только после этого разрешены открытие по правилам владельца и сигнал ready.
4. Отмена, закрытие выбора, отказ валидации, потеря назначения, смена раскладки, disable или тайм-аут до принятия инвалидируют поколение. WorkspaceSession удаляет временное размещение, освобождает оба резерва и возвращает фокус в прежнюю группу, если она существует. Отмена повторяема; поздний UUID игнорируется. В документе не остаётся пустого тайла, фиктивного UUID или несохранённой правки. Если размещение отклонено, привязку и открытие не выполняют. После принятия действуют обычные состояния доступа и потери связи. Сбой последующей записи раскладки обрабатывается штатным механизмом сохранения.

### Два вида одного Telegram-чата

Различать команды «Показать» и «Добавить вид». Первая адресует конкретный panelId и активирует или возвращает его из скрытых. **Каждый** явный выбор через «Добавить вид Telegram» получает новый panelId и instanceId на шаге резервирования, даже если владелец вернул уже открытый UUID. Для этой команды пропускаются поиск panelIdOfRef и activateTab из `workspace-session.ts:282`; picker не превращает её в переход к первому совпадению (`workspace-session.ts:204`). При принятии реестр применяет семантику open(ref, {newView: true}) с резервом ID и проверяет provider.multipleViews (`src/core/panels/registry.ts:157`). Telegram объявляет multipleViews=true. Для одноэкземплярного Zoom совпадение с существующим звонком снимает резерв выбора и показывает прежний вид; его iframe остаётся на месте.

В сохраняемом документе два разных panelId могут ссылаться на одинаковый PanelRef (`src/core/workspace/operations.ts:176`). При восстановлении и ленивом открытии вкладки `workspace-session.ts:382` связывает экземпляры по panelId. Для каждого ещё не связанного panelId многоэкземплярного Telegram требуется новый вид даже при наличии совпадающей ссылки. В частности, существующая проверка taken на строке 388 не должна отклонять второй тайл из-за повторного использования первого instanceId. При повторной активации **того же** panelId берётся уже связанный экземпляр. resourceRef остаётся общей идентичностью чата, а локальные черновики, файлы, выделение и прокрутка разделены по идентичности вида.

**Минимальные сообщения версии 1.** Контейнер создаёт Чертог, пустая область остаётся доступной для кнопки повтора и штатного перехода. Стороны обмениваются закрытыми вариантами событий на уровне адаптеров:

| Направление | Поля и эффект |
|---|---|
| Чертог → overlay владельца | Объявление содержит тип провайдера, instanceId, номер попытки, узел и режим выбора или разрешения resourceRef. Сигнал скрытия отдельно сообщает, доступен ли тайл для взаимодействия. Запрос закрытия только открывает диалог владельца. |
| Владелец → Чертог | Ответ содержит тот же тип, instanceId и попытку. Выбор возвращает только resourceRef, готовность — состояние ready, отказ — конечный код denied/ended/lost, отзыв — поколение регистрации. На диагностику выводится код. Текст ошибок SDK может включать приватные данные и остаётся на экране владельца. |
| Рестарт или потеря стороны | Подписка появляется до запроса текущих объявлений. Узел принадлежит ровно одному принятому типу и попытке. На замену поколения владелец отписывается и блокирует ввод старого вида, а Чертог обнуляет привязку попытки. Повторное подтверждение после отзыва отвергается обеими сторонами. |

### Ссылки и совместимость

Ниже новые типы. У старых `telegram`, `zoom`, `remote-ssh`, `remote-rdp`, `remote-vnc` сохраняется сегодняшнее значение карточек с пустыми параметрами (`plugins/chertog/src/core/panels/entry-card.ts:1`, `src/adapters/bb/app/card-source.ts:169` внутри плагина). Это исключает запуск сессии при чтении старой раскладки. Каждый новый PanelRef имеет форму `{provider, params: {resourceRef}}`; для **каждой** строки одинаковая закрытая paramsSchema — `z.strictObject({resourceRef: z.uuidv4()})` поверх общей проверки `plugins/chertog/src/core/panels/ref.ts:128`.

| provider | К чему владелец привязывает resourceRef | Повторный вид и восстановление |
|---|---|---|
| telegram-chat | Аккаунт, чат и при наличии тема | Отдельный экземпляр UI на каждый выбор, включая повтор того же чата. Ссылка восстанавливает только разрешённую цель. |
| zoom-call | Выбранная пользователем встреча в своём аккаунте | Один активный вид данной встречи, повторный выбор показывает существующий. При reload только приглашение войти. |
| remote-ssh-live | Запись рабочего стола/профиль, при необходимости гость PVE | Для выбранной живой сессии owner разрешает точную пару generation/sessionId и новый attach. При неоднозначности — повторный выбор. |
| remote-rdp-live | Цель RDP | Владелец проверяет активную сессию и допускаемое число видов. Каждому принятому attach выдаётся свой viewId. |
| remote-vnc-live | Выбранная графическая консоль гостя | Единственный потребитель потока за жизнь консоли. Занятый вид можно показать на месте. Автоперехват и второй attach запрещены. |

Один ресурс с несколькими живыми сессиями требует отдельных непрозрачных ссылок на выбор пользователя. У провайдера долговечна цель, а оперативная привязка к конкретной сессии истекает вместе с поколением. Один session/meeting должен иметь каноническую привязку для подсчёта последнего вида, в том числе если уже открыт штатный экран. В раскладке отсутствуют номер встречи, chatId, имя машины, sessionKey, attachId, viewId и credential. Индикатор адресата в Чертоге использует нейтральную подпись; реального получателя показывает владелец внутри тайла.

При активном глобальном аккаунте перепроверять привязанную учётную запись на сервере при **каждой** операции. Если backend обслуживает только текущий аккаунт, отказать панели другого аккаунта до поддержки адресного backend. Два чата одного аккаунта не должны менять глобальный адресат. Подписки фильтруются по привязке; добавление файла требует явного указания конкретного черновика, отправка остаётся отдельным действием.

**Zoom.** В `plugins/zoom/app.tsx:18` owner overlay и календарь используют один реестр окна; в `src/ui/calendar-screen.tsx:39` перенести владение active-звонком из маршрута в overlay. Календарь только выбирает встречу. Единственный `src/ui/call-panel.tsx:89` с iframe на строке 193 живёт под одним неизменным физическим родителем весь звонок. Если звонок начат в штатной странице, переключать геометрию его исходного хоста или показать исходный вид. Смена portal target создала бы новый iframe. В `server.ts:137` подготовка выполняется после пользовательского входа и проверки доступа, подпись/ZAK выдаются только владельцу; закрыть такие RPC от межплагинных вызовов. Для внутреннего сообщения с данными входа усилить существующую проверку source (`call-panel.tsx:102`): также проверить точный origin из `src/core/redirect.ts:30`, отправить с этим targetOrigin, принять ready однократно для ожидаемого поколения. Ограничение адреса loopback сохраняется. Билеты `src/adapters/bb/http-routes.ts:27` относятся к отдельному открытию в браузере. Отказ media, timeout, failed, joined и ended сообщает Zoom. Последний вид предупреждает даже при неизвестном исходе входа; повторный leave идемпотентен. Восстановления медиа после потери документа нет.

**Remote Hub.** В `plugins/remote-hub/app.tsx:31` переиспользовать useLiveApi в owner overlay. В `src/adapters/bb/service.ts:1290` разрешать выбранную цель с проверкой поколения и состояния; `src/adapters/bb/rpc-handlers.ts:34` сохраняет границу caller. Проверка host key, сертификата и прав остаётся штатной. `src/ui/live-session.tsx:30` уже различает типы; встроенную карточку VNC на строке 52 нельзя считать консолью. Для SSH использовать `src/ui/ssh-terminal.tsx:136` и cleanup на строке 213. Перестройка не делает attach. Новый явный attach к живому ключу получает ограниченный снимок и последующий поток, без повторного ввода и гарантии старого выделения. Для RDP переиспользовать `src/ui/rdp-canvas.tsx:203` и выдачу viewId в `service.ts:1093`; detach снимает вид, не завершает соединение. Подтвердить полный первый кадр нового вида. Контроль ввода и Take control остаются в Remote Hub. В `src/ui/watch-beat.ts` учитывать реальную видимость тайла и фокус окна при выдаче heartbeat. Для VNC переиспользовать `src/ui/vnc-view.tsx` под единственным постоянным родителем. При уже подключённом штатном просмотре отказать второму потребителю. Последний detach закрывает relay (`service.ts:1208`) и требует предупреждения; после утраты консоли возможен только новый явный запуск. При устаревшем ключе, отказе доступа и перезапуске helper не создавать новую сессию автоматически.

В каждом из трёх пакетов добавить собственный `src/adapters/bb/embed-overlay.tsx`; сопоставление UUID с ресурсом и операции с данными выполняет только владелец. Пакеты сверяют одну версию протокола и примеры сообщений в тестах, без импортов между плагинами. Порты и семантика состояния принадлежат core, визуальные компоненты получают данные и callbacks через props. SDK-хуки, регистрация и транспорт остаются в app.tsx, server.ts и adapters/bb.

## Узкое предложение хосту для карточек

Добавить в BbNavigate публичную операцию перехода по зарегистрированным pluginId, path и необязательному subPath в том же документе. Хост валидирует регистрацию, кодирует сегменты и сам обновляет историю. Метод возвращает успех после принятия перехода либо явную причину отказа при выключенном владельце, неизвестном маршруте или ограничении размещения. Переход не создаёт сессию и не выбирает тайл для замены без согласия. Сейчас `plugins/chertog/src/adapters/bb/app/card-source.ts:22` копирует форму history state, вызывает pushState и посылает popstate. Это зависимость от реализации маршрутизатора. Штатный toPluginPanel адресует собственный раздел; sidebar.activate работает в своём слоте (`bb-plugin-sdk-app.d.ts:19739`, `:24705`). Контрактный тест хоста должен открыть чужую страницу из карточки, пройти Back/Forward и подтвердить неизменный document и boot ID припаркованной панели. Для portal-вида этот переход не требуется.
