# Этап C. Окна и мониторы

**Решение для SDK 0.6.157 и BB Desktop 0.50.1.** Два уже открытых окна одного сервера могут показывать разные раскладки и согласовывать передачу через сервер плагина. В Desktop пользователь может открыть второе окно штатным пунктом **New Window**. У плагина нет контракта, который по нажатию «Отстыковать» создаёт именно окно BB и возвращает его идентичность. Выбор дисплея для существующего окна, проверяемый возврат при горячем отключении и передача существующего native view требуют поддержки оболочки. Эти операции и перенос панели — разные строки проверки. Исследование статическое, Desktop и провайдеры здесь не запускались.

Основания и порядок приёмки заданы в [разделах 1, 4 и 5 задания](spec.md), [сверке версии SDK](sdk-version.md), [обзоре провайдеров](discovery-providers.md) и [описании изолированного стенда](e2e-stand.md).

## Передача одной панели между открытыми окнами

Для Чертога достижим один логический владелец размещения на сервере. Для гарантии единственного действующего ввода нужен провайдер, который действительно отклоняет ввод прежнего поколения, либо подтверждённое отключение старого ввода до включения нового. Два самостоятельно смонтированных редактируемых компонента и запись owner в KV этой гарантии не дают. Нижеследующее — проект протокола, требующий реализации и приёмки.

1. **Подготовить.** В выбранном окне назначения открыть пустое место для безопасной ссылки на панель. Связать одноразовую передачу с обоими экземплярами документов, instanceId, поколением владельца и ревизией. Проверить доступ к той же существующей сессии. Владелец в источнике сохраняет ввод. В назначении разрешена подготовка без активного ввода и без создания второй доменной сессии.
2. **Подтвердить.** Владелец подтверждает конкретное назначение. Окно назначения сообщает готовность только после проверки идентичности провайдером. При отказе, закрытии назначения или истечении срока до переключения снять резерв. Ввод остаётся у источника.
3. **Переключить.** Блокировать старый ввод с подтверждением, атомарно заменить владельца по ожидаемому поколению, включить новый ввод с разрешения провайдера. Отзыв управления Remote Hub сохраняет силу. При закрытии назначения до завершения сверить состояние передачи на сервере и вернуть ввод источнику после исключения старого права назначения. При потере связи показать неопределённый результат, повторить чтение статуса по тому же ID. Дублированные и запоздалые подтверждения не меняют владельца.
4. **Освободить источник.** Только после подтверждения работающего назначения убрать прежний вид, сохранив доменную сессию. При штатном закрытии отстыкованной панели предложить обратную передачу. Если вернуть некуда, оставить окно открытым или завершить по явному выбору. При падении процесса перепроверить владельца и существование сессии. Повторный вход во встречу, reconnect и повтор команды автоматически не выполнять.

**Тред.** Публичный `ThreadChat: ComponentType<ThreadChatProps>` принимает существующий threadId (`bb-plugin-sdk-app.d.ts:24863`, `bb-plugin-sdk-app.d.ts:23752`). В новом документе можно показать тот же тред. До допуска проверить привязку composer, черновик, фокус и ровно одного адресата клавиатуры. На время подготовки использовать неинтерактивную поверхность. Результат для курсора, вложений и несохранённого ввода требует отдельного опыта.

**SSH.** Remote Hub владеет helper-сессией, ключ включает generation и sessionId. Его штатная поверхность умеет attach к существующей сессии и ограниченный replay. Публичной встраиваемой SSH-панели с подтверждением готовности и отзывом старого ввода у Чертога сейчас нет. Кандидат для отстыковки после адаптера и опыта с тем же PTY, PID, нумерованным выводом и отзывом управления. В постоянной схеме сохранять только безопасную ссылку на цель. RDP, VNC, Zoom и иные непроверенные виды оставить без действия отстыковки с объяснением и возможностью переместить целое окно штатно. [Обзор Remote Hub и браузерных поверхностей](discovery-providers.md)
