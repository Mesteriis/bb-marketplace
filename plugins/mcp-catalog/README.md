# MCP Каталог

Плагин BB: страница «MCP Каталог» в боковой панели. Ищет MCP-серверы в трёх каталогах (официальный реестр, GitHub MCP Registry, Docker MCP Catalog), отдаёт их на проверку агенту, хранит принятые в git-коллекции и ставит только принятое как пакеты моста Agent Plugins. Сам ничего не запускает: серверы живут на мосту.

Подробное описание страницы для пользователя: `PLUGIN_OVERVIEW.md`.

## Настройки

Обе пустые по умолчанию; пока они не заданы, страница показывает, что задать, а действия, которым нужна настройка, выключены.

- `marketplaceRepoPath` — рабочая копия репозитория маркетплейса (checkout на `main`, без незакоммиченных правок). Коллекция читается из `origin/main` этой копии, принятые записи сливаются в её `main`.
- `marketplaceProjectId` — проект маркетплейса в BB; в нём запускаются треды проверки.

Задаются командой `bb plugin config <id> set <ключ> <значение>`.

## Каталоги

Поиск идёт в три каталога; на странице флажки выбирают, какие из них спрашивать (хотя бы один должен остаться включённым).

- **Официальный** — `https://registry.modelcontextprotocol.io/v0/servers`.
- **GitHub** — GitHub MCP Registry, `https://api.mcp.github.com/v0.1/servers`; тот же формат, что у официального. Сервер, который есть в обоих, показан один раз с двумя пометками, проверка и принятие берут запись официального реестра.
- **Docker** — Docker MCP Catalog, один файл `https://desktop.docker.com/mcp/catalog/v3/catalog.json`. Кэшируется в памяти на 6 часов, ищется локально по ключу, названию, описанию и тегам, 30 записей на страницу. Имена записей `com.docker.mcp/<ключ>`, версия `sha256-<12 символов digest>`; проверка и принятие снова берут запись из Docker.

Недоступный каталог не ломает поиск: остальные отвечают, а над списком показано предупреждение.

Записи Docker, которые каталог не может запустить, показаны с причиной, а «Проверить» для них выключена и `startReview` их отклоняет. Причины:

- «тип poci не поддерживается»;
- «нужны тома (volumes)»;
- «шаблоны в command не поддерживаются»;
- «переменная <имя>: смешанный шаблон» (значение переменной смешивает текст и шаблоны);
- «некорректное имя переменной <имя>»;
- «образ без закреплённого digest»;
- «некорректный образ»;
- «удалённый адрес с заголовками пока не поддерживается»;
- «нужен вход OAuth» (другого способа запуска нет);
- «нет ни образа, ни удалённого адреса»;
- «запись каталога повреждена».

Образы Docker закреплены по digest, для запуска нужен установленный Docker. Правило `run.allowHosts` каталога Docker не применяется: плагин не ограничивает сеть сервера, а агент проверки только перечисляет эти хосты в отчёте.

## Как это работает

1. **Проверка.** «Проверить» на странице поиска запускает тред проверки выбранной версии в проекте маркетплейса. Агент не запускает код сервера: он читает закреплённую версию (для Docker — образ с digest) как данные и пишет в своё рабочее дерево три файла в `mcp-collection/<имя>/` (`server.json`, `review.md`, `entry.json`) и строку в `mcp-collection/index.json`. Ничего не коммитит. Проверки хранятся отдельно для каждой пары «имя и версия».
2. **Принятие.** Когда тред закончил, владелец жмёт «Принять» (или «Отклонить»). Каталог сверяет `server.json` с записью реестра для проверенной версии, коммитит запись на ветке проверки, сливает её в `main` основной копии и делает push. Новая версия уже принятого сервера заменяет его строку в индексе. Если принятие оборвалось после коммита, повтор использует тот же коммит.
3. **Установка.** Ставить и обновлять можно только запись, которую принял этот каталог и чей коммит принятия есть в `origin/main`. Форма показывает переменные, объявленные сервером; секреты вводятся в полях-паролях и в интерфейс не возвращаются. Установка пишет локальный пакет Agent Plugins и файл ключей (права 0600) в данных плагина и просит одобрения в мосту. При обновлении переменные, появившиеся в новой версии, получают значения по умолчанию, а обязательная без значения останавливает обновление.

Если повтор прерванного принятия теперь всегда отвечает «посторонние коммиты», верните ветку проверки на `main` (reset) и запустите проверку заново.

## Устройство

- `src/core` — чистая логика: схемы (zod), порты, сценарии (`service.ts`, `install.ts`, `review.ts`), генерация пакета. Без обращений к хосту.
- `src/adapters/bb` — всё, что говорит с хостом: `bb agent-plugins`, треды, git, файлы ключей и пакетов, реестр по HTTP.
- `src/ui` — страница; получает данные и действия только через props.

`tests/architecture.test.ts` следит за этими границами.
